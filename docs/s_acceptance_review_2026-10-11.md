# S 검토 — 방향 수용, 재실행 경계 보완

작성: Codex, 2026-10-11 KST. 대상: S 인수인계, extract/daily_run_state 코드, S0 시험, S3 평가 문서. 운영 미관측이며 원격 CI 재조회는 하지 않았다.

## 판정

타임아웃·재시도 가능한 5xx를 부분 성공에 포함하는 변경은 수용한다. 모델 일시 장애라는 같은 범주이며, 정상 처리된 근거만 사용하는 조건을 유지한다. 401/403·응답 해석 오류·원장 오류는 포함하지 않는다. 타임아웃의 12시간 대기는 현재 유지하되 해당 항목은 저녁 복구 기회에 처리되지 않을 수 있음을 명시한다.

429를 제공자 차단·deferred로 두는 기존 동작도 수용한다. 모델 호출 차단과 이미 검증된 위험 신호의 전송 허용은 별개다. 정상 처리 0건인 429 대기도 기존 정책상 종료0일 수 있으므로 '정상 처리 0이면 언제나 차단'이라는 요약은 정정한다. pending이 있으면 partial로 표시하고 모델 복구는 차단 해제 전까지 요청0을 유지한다. 429를 추출 완료로 보고하지 않는다. 제공자 실제 할당량은 여전히 미확인이다.

**S0 최종 인수는 아래 세 경계 보완 후 진행한다. S3는 초기 검토표로 인수하되 원문 연결과 해석을 보완한다.** 운영 확인을 위한 실제 발송·전체 재실행은 요청하지 않는다.

## 직접 검증

- S0 관련 unittest 28개 통과(0.540초). 606개 전체·깨끗한 복제본·CI 통과는 구현 담당자 보고이며 이번에 재실행한 결과가 아니다.
- [추가 재현](s_review_probe_2026-10-11.py)은 기존 가짜 모델 fixture·임시 상태만 사용한다. 실제 모델·SEC·Yahoo·Telegram 요청 없음. 이 스크립트는 관측값 출력용이며 종료0이 결함 해결을 뜻하지 않는다.
- 작업 시작 시 저장소 변경 없음. 이번 변경은 검토 문서·재현 스크립트·STATUS뿐이다.

## 1. 대기 중 재실행이 미해결 오류를 성공으로 바꿈

재현 결과:

| 입력 | 첫 실행 | 즉시 빈 입력으로 재실행 |
|---|---|---|
| 1항목 503, 오늘 정상 처리0 | 종료1/model_unavailable | 종료0/ok, processed_today=0, pending=1 |
| 1항목 정상+1항목401 | 종료1/error | 종료0/ok, processed_today=1, pending=1 |

원인: extract_outcome은 이번 호출의 failed/unserved만 본다. next_retry_at 전의 항목은 선택에서 빠져 실패 카운터0이 되고, 미해결 오류가 남아도 notify가 열릴 수 있다. 제한된 recover에서는 대기 검사로 회피하지만 기존 auto/수동 extract 경로에서 재현 가능하다. 실제 오발송 관측은 아니다.

수정: scripts/extract.py와 tests/test_s0_partial_extract.py. 결과는 이번 호출뿐 아니라 해당 일간 입력에 연결된 미해결 상태와 당일 저장 결과를 함께 판정한다. 원장에 실패 분류·발생일/실행·입력 식별을 보존한다. 과거 오류를 무기한 현재 장애로 끌어오지 않되 같은 입력의 해결되지 않은 오류는 무시하지 않는다. 새 정상 응답·명시적 원인 해결·유효기간 만료 때만 해소하며 근거를 기록한다. 503 무응답은 model_unavailable, 401/형식 오류는 error가 유지돼야 한다. 정상 처리+일시 장애는 partial, 429/순수 예산 대기는 위 승인한 별도 규칙을 따른다. 빈 실행·예산0·raw 없음·새 항목 성공과 기존 오류 공존을 시험한다.

## 2. auto의 실패 분기가 복구 제한을 우회

재현: 오늘 recoveries 2회 소진, extract=failed/model_unavailable 상태에서 auto 계획은 extract=failed, notify=blocked, alerts/views=dependency_rerun을 반환한다. 일반 실패 분기가 recovery_room/재개 시점 검사보다 먼저 실행된다. 이 계획은 extract_resume 이유가 아니어서 복구 횟수에도 추가되지 않는다.

수정: scripts/daily_run_state.py와 tests/test_s0_recover.py. 오늘 이미 시도한 모델 장애 extract는 failed/partial 모두 같은 복구 조건·간격·누적 한도를 사용한다. 최초 일간 not_run은 이 제한에 묶지 않는다. 명시적 daily/redo의 기존 의미는 별도로 유지하고 예외 실행 사유를 기록한다. auto의 초안 전용 재개도 공통 복구 한도와 draft_resume_max를 함께 지키고 카운트한다. 모델 대기·할당량·예산0·2회 소진·59분 간격에서 auto/recover 모두 불필요한 모델 단계와 그 종속 단계 계획0을 시험한다. 독립적으로 필요한 다른 단계는 막지 않는다.

## 3. 저장된 복구 계획이 중단되면 recover가 이어받지 못함

재현: recover 계획 저장으로 extract=pending, recoveries=1이 된 직후 프로세스가 중단됐다고 가정하면 61분 뒤 recover 계획은 빈 결과다. extract_recoverable은 success/failed만 허용한다. 기존 시험은 카운터 저장만 확인하고 실제 재개는 확인하지 않았다.

수정: 같은 파일·시험. 저장된 복구 실행의 원인과 미완료 단계(pending/started)를 보존하고 기존 단일 작성자 잠금 아래 다음 recover가 이어받도록 한다. 최초 계획의 예약 횟수는 되돌리거나 새로 초기화하지 않는다. 같은 계획의 계속 실행은 새 복구 슬롯을 소비하지 않되 모델 요청 예산은 실제 요청마다 계속 차감한다. 기다림·제공자 차단·원장 일관성은 다시 검사한다. extract 완료 후 notify/views 전 중단도 이미 끝난 수집을 반복하지 않고 남은 단계만 이어간다. 불확실한 발송은 기존 uncertain 잠금을 따른다. 계획 저장 직후, 모델 단계 직후, 알림 후 화면 전 중단과 KST 날짜 전환을 시험한다. 전날 계획을 오늘 새 일간 완료로 세지 않는다.

## S3 해석·증거 보완

후보 순위는 추가 조사 순서로만 유지한다. 이번 검토는 제공된 평가 문서의 논리 검토이며 최신 기업 사실을 외부 원문으로 다시 확인한 투자 분석이 아니다.

1. DHT 표의 1.23/2.50은 약49.2%로 '절반 이상'이 아니다. '즉 시장은 운임 급락을 가정'은 삭제하고 '기간·회계기준·주식 수·일회성·계절성을 맞춰야 비교 가능하며, 운임 정상화 기대는 검증할 가설'로 쓴다. 원문 회사 실적과 회계기준 미표시 Yahoo 예상치를 바로 연결하지 않는다. FRO/INSW도 같은 원칙이다.
2. 원인 그룹은 유조선(DHT/FRO/INSW)과 정유(PBF)를 구분한다. 공통 거시 노출은 기록하되 업종·사업별 이익 경로가 다르면 단일 원인으로 확정하지 않는다. BP는 원문 미확보라 같은 원인을 확인했다고 셀 수 없다. 동일 회사 주장이 여러 문서에 반복된 것과 서로 다른 회사의 관측도 구분한다.
3. BP/SPCX는 규모만으로 영구 제외하지 않는다. 프로젝트 원칙은 산업·절대 규모보다 회사 규모 대비 이익 변화·시장 미반영·지속성이다. 이번에는 원문/이익 경로/기대차 증거 부족에 따른 조사 우선순위 보류로 기록한다. 초대형주 일괄 제외 필터는 이번 지시에서 추가하지 않는다.
4. 8개 각각 알림 이벤트 ID·당시 카드 버전·공식 문서 ID·원문 URL·발표일·근거 인용 위치를 표에 연결한다. 특히 SPCX의 회사 동일성·상장/시가총액 등은 티커만으로 단정하지 않는다. 저장 원문이 뒷받침하지 못하는 설명은 미확인으로 바꾼다.
5. '원문 7개가 있었지만 예산 때문에 8건 모두 설명 없음'은 원문 최초 확보 시각·알림 시각·큐의 보류 사유로 확인한다. 10/10에 저장돼 있었다는 사실만으로 10/6 발송 당시 준비돼 있었다고 결론 내리지 않는다. 모델 대기·회사 식별·기간/검증 거절을 예산 부족과 분리한다.

## 다음 우선순위

세 재실행 경계 보완과 S3 근거표 정리를 병행한다. S2는 실제 일간/복구에서 SHA·outcome·quality·notify 적격/전송 건수·pending 감소·복구 슬롯/실제 기회 수를 기록한다. S1 평가 때문에 운영 몫을 줄이지 않는다.

다음 발굴 품질 작업은 (1) VSEC EPS 정의 변경 경고와 비교 가능 여부, (2) 알림 후보의 저장 원문 초안 우선 처리, (3) 근거가 확인된 공통 원인의 묶음 표현 순이다. 기존 하루6회 안에서 우선순위만 조정하되 오래 기다린 후보와 folded 몫을 모두 빼앗지 않는 안을 설계한다. 근거 없는 원인 문구를 자동 생성하거나 알림을 무기한 보류하지 않는다. PBF·유조선·VSEC는 근거표가 채워진 범위에서 후속 조사하며 이 문서만으로 추적 추천 승인하지 않는다.
