# V 제안 — 텔레그램 상호작용: 알림에 대한 사용자 판단 기록과 응답 지연 단축 (2026-10-11)

작성: Claude, 2026-10-11. 사용자 요청("상호작용이 되어야 좋은 거 아닌가")에서 출발한 **Codex 검토용 제안**이다. 구현하지 않았다. 설계·우선순위·지시서는 Codex가 정한다.

## 왜 필요한가

- 지금 텔레그램은 알림 발송과 명령 몇 개(/candidate, /track, /screen, /list, /history, /data, /help)만 처리한다. 명령은 예약 실행 때만 읽어서 답이 몇 시간 늦다.
- 사용자가 알림을 보고 내린 판단(관심 없음, 추적 등)은 대화로만 전해지고 원장에 남지 않는다. 예를 들어 10/11 AXTI는 같은 날 '제외'했다가 '다시 포함'했는데, 이 판단은 문서와 STATUS에만 있다.
- U 주기의 결론은 '시장 미반영을 확인할 자료가 없다'였다. **알림마다 남는 사용자 판단은 엔진이 쓸모 있는 후보를 냈는지 평가할 가장 직접적인 자료**다. 사후 수익률은 평가 기간이 차야 쓸 수 있지만, 사용자 판단은 바로 쌓인다.

## 현재 동작(현행 소스 확인)

- `scripts/telegram_cmd.py`
  - `get_updates`: `allowed_updates: ["message"]`로 메시지만 받는다.
  - `process_updates`:
    - 허용 채팅(`TELEGRAM_CHAT_ID`)의 메시지만 받는다.
    - 지원 형태로만 바꿔 `command_queue.json`에 저장한다. **원문 채팅은 저장하지 않는다.**
    - 형식에 맞지 않는 글은 모두 `/help`로 바뀐다. 그래서 알림에 일반 답장을 하면 명령어 목록이 회신된다.
    - 오프셋 저장 → 처리 → 회신(`send_reply`, HTML) 순서다. 실패하면 남겨 두고 다시 시도한다.
  - 답장 대상(`reply_to_message`)은 읽지 않는다.
- 알림과 메시지 ID 연결: `candidate_alerts.json`의 각 이벤트에 `message_id`가 있다(예: 165~167 → DHT·FRO·INSW 새 발굴). 정정 안내 168은 `correction_notices.json`에 있다.
- 실행 시각
  - 명령 처리는 워크플로의 `commands` 단계다(모든 모드에서 실행).
  - PC 타이머: 명령 확인 03:23·15:23·21:23 KST, 일간 09:17 KST.
  - GitHub 예약: `23 */6 * * *`(recover). 예약은 흔히 몇 시간 늦는다.
  - 동시 실행 그룹은 `research-state-writer`다.

## 제안 ① — 알림에 답장으로 판단 남기기(모델 호출 0)

**동작.**
- 사용자가 후보 알림 메시지에 **답장**으로 정해진 낱말 하나를 보내면, 답장 대상 `message_id`로 알림 이벤트를 찾아 처리한다.

| 답장 | 처리 | 기록 |
|---|---|---|
| `추적` (또는 `/track`) | 기존 `handle_track_candidate`와 같다(그 이벤트의 candidate_id) | 판단: track |
| `관심없음` (또는 `패스`) | 상태 변경 없음 | 판단: dismiss |
| `자세히` (또는 `/candidate`) | 기존 `/candidate`와 같다 | 판단: detail(관심 신호) |
| `보류` | 상태 변경 없음 | 판단: hold |
| 그 밖 | 지금처럼 `/help` 회신. 원문은 저장하지 않는다 | 없음 |

**판단 원장(새 파일, 추가만).** `data/processed/candidate_feedback.json`, 판단 1건당:
- `update_id`, `received_at`, `reply_to_message_id`
- `event_key`, `candidate_id`, `candidate_version`(발송 당시)
- `verdict`(track/dismiss/detail/hold), `source: "telegram_reply"`
- 원문 텍스트는 저장하지 않는다. 지금 원칙과 같다.
- 같은 이벤트에 판단이 여러 번 오면 모두 남기고, 마지막 판단을 현재 판단으로 본다. 오늘 AXTI처럼 번복하는 경우다.

**쓰임.**
- 발견 시점 보고에 판단별 분포를 표시한다(전체 알림 대비 track·dismiss·무응답 수). 사후 수익률이 차면 판단별로 따로 본다(사용자 판단과 실제 결과의 비교).
- 카드에 '사용자 판단: 관심없음(날짜)'을 표시한다. 알림 재발송 규칙은 바꾸지 않는다(범위 밖).

**예외.**
- 답장 대상이 알림이 아닐 때(정정 안내 168, 명령 회신 등): 판단을 기록하지 않고 '알림 메시지에 답장해 주세요'라고 회신한다.
- 답장 대상 메시지의 이벤트가 `uncertain`·`failed` 상태일 때: Codex가 정한다. 사용자가 받은 메시지라면 판단은 유효해 보인다.
- 허용 채팅이 아니면 지금처럼 무시한다.
- 한 회신 실패가 판단 기록을 막지 않게 한다. 순서는 판단 원장 저장 → 오프셋 → 회신이다(지금 대기열 원칙과 같다).

**대상 파일(예상).** `scripts/telegram_cmd.py`(답장 대상 읽기·낱말 매핑), 새 원장, `scripts/discovery_timing.py`(보고), `scripts/candidates.py`(카드 표시), README, 시험.

**비용.** 모델 0, 외부 요청은 기존 회신 1건뿐이다.

## 제안 ② — 응답 지연 단축(모델 호출 0)

- 선택지 A: PC 타이머 명령 확인을 하루 3회에서 15~30분 간격으로 늘린다(`mode=commands` dispatch).
  - 장점: 답이 30분 안팎으로 온다.
  - 비용·위험
    - PC가 켜져 있어야 한다.
    - dispatch마다 실행·상태 커밋이 생긴다. 30분이면 하루 최대 48회다.
    - 일간 실행과 같은 동시 실행 그룹에서 대기가 늘 수 있다.
    - dispatch에 쓰는 GitHub 토큰이 평문 파일(`../setup-24h-timer.ps1`)에 있다는 미해결 문제가 커진다. 먼저 교체해야 한다.
- 선택지 B: 명령이 없으면 커밋하지 않도록 해서 A의 커밋 잡음을 줄인다. 지금 오프셋·대기열이 바뀌지 않으면 커밋이 생기는지는 확인이 필요하다.
- 선택지 C(권하지 않음): 상시 웹훅 서버(Cloudflare Worker·Apps Script 등). 즉시 응답이지만 새 실행 환경과 비밀값 관리가 늘고, 단일 작성자 원칙과 충돌할 수 있다.

## 제안 ③(나중) — 자유 질문 답변

- "AXTI 왜 올렸어?" 같은 질문에 저장된 카드·판정 문서로 답한다. 질문마다 모델이 필요하다.
- 하루 20회 예산과 429 차단 개편(T 계획) 전에는 운영 예산과 충돌하므로 미룬다. 그 전에는 질문을 이 대화(Claude)나 Codex로 받는다.

## 권하는 순서와 완료 기준(제안)

1. **①을 먼저 한다.** 완료 기준:
   - 알림 답장 `관심없음`이 원장에 1건 남고 상태는 바뀌지 않는다.
   - 답장 `추적`이 기존 /track과 같은 결과를 낸다.
   - 알림이 아닌 메시지에 답장하면 기록 없이 안내만 회신한다.
   - 원문이 어디에도 저장되지 않는다.
   - 같은 업데이트를 다시 처리해도 판단이 중복 기록되지 않는다.
   - 보고에 판단 분포가 나온다.
   - 가짜 업데이트로 시험하고 실제 발송은 하지 않는다.
2. **②는 토큰 교체 뒤**, A+B로 간격을 정한다. 완료 기준: 명령 없는 실행은 커밋하지 않고, 일간 실행 대기에 영향이 없다.
3. ③은 T 계획 이후.

## Codex가 정할 것

- 낱말 목록과 판단 종류. 4개면 충분한지, '틀림'(근거 오류 신고)을 따로 둘지.
- 판단을 엔진 평가에 어떻게 쓸지. 보고 분포만 낼지, 카드 정렬·알림 선택에도 쓸지. 이 제안은 보고·표시까지만이다.
- ②의 간격과 토큰 교체 선행 여부.
