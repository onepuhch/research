## 3. K1 — 주체 검증과 제한된 과잉 거부 보완

### K1-1. 숫자의 귀속 범위를 확인한다

- subject를 issuer로 주었다는 이유만으로 회사 수치로 믿지 않는다. 주장의 **지표·수치가 놓인 절**에서 명시된 귀속을 확인한다.
- `from <business>, which was sold ...`, `<named business/segment/subsidiary> revenue ...`, discontinued/divested operations 등 **명확히 특정 사업에 연결된 수치**를 issuer 주장으로 받으면 `subject_scope_conflict` 등 구체적인 사유로 거부한다.
- 숫자 여러 개가 같은 사업에 연결된 NBR식 열거(`revenue ... EBITDA ... operating income ... from Quail Tools, which was sold ...`)도 처리한다. 마지막 수치만 보호하면 안 된다.
- 원문이 특정 사업의 수치인데 모델이 issuer라고 쓰면 `core=false`만 붙이고 수용하는 것으로 끝내지 않는다. 표시되는 숫자 주장 자체를 거부한다. 모델의 subject를 자동으로 segment로 바꾸는 보정도 하지 않는다.
- 귀속을 확인할 수 없는 모호한 숫자는 미검증으로 보류한다. 예외 규칙을 기업명 NBR/Quail Tools에만 고정하지 않는다. 문서 수집이나 별도 모델 호출로 주체를 확인하려 하지 않는다.
- 회사 전체 수치와 사업 수치가 같은 문장에 함께 있을 때 회사 전체 수치까지 일괄 거부하지 않는다. 예: 회사 전체 revenue가 명시되고 뒤에 매각 사업 기여분/제외 설명이 붙은 경우, from international operations/higher demand 같은 원인·지역 설명은 회사 전체 매출의 반증이 아니다.
- subject=segment/subsidiary이며 해당 이름과 수치 귀속이 원문에 명확한 경우는 보조 근거로 유지할 수 있다. 회사 전체 핵심 초안과 구분한다.

필수 회귀: NBR 실제 문장의 revenue/EBITDA/operating income 각각 issuer 거부, 다른 사업명으로 바꾼 합성 경계 사례, 정확한 사업 주체 허용, 명시적 회사 전체 수치 허용, 회사 전체+사업 기여분 동시 문장, 단순 'from higher demand' 오탐 방지. 다른 저장 원문(MPC 자회사, CORT 제품 등)도 영향을 확인한다. 합성 사례는 합성이라고 기록한다.

`test_known_miss_divested_unit_revenue_as_issuer`에서 expectedFailure를 제거하고 일반 테스트로 통과시킨다. 해당 시험을 삭제하거나 예상실패로 계속 숨기지 않는다. 테스트 수는 실행/통과/예상실패를 정확히 보고한다.

### K1-3. AEHR의 설명 삽입구

재현 문장은 `Effective backlog, including bookings since May 29, 2026, is $100.6 million.`이다. metric=backlog, figures=$100.6 million이 bookings의 수치로 판정되어 거부된다.

- 명확히 닫힌 `including ...` 설명 삽입구 뒤에 원래 지표의 술어와 수치가 이어지는 경우, 삽입구의 지표명이 본문의 수치를 가로채지 않도록 위치 관계를 확인한다.

5. 감사 사본 저장 실패는 기존처럼 별도로 드러내되 원래 예외를 가리지 않는다. response 크기 제한·비밀값 비기록·원자 저장을 유지한다.

완료 증거: `block_id=[]` 응답에서도 감사 사본이 존재하고, 필드 오류가 기록되며, 같은 응답의 정상 claim은 유지되는 시험. 내부 validate_draft를 의도적으로 예외 처리한 시험에서도 원응답이 남아야 한다. '감사 저장 시도'와 'CTX 운영 저장 성공'은 별도 상태다.

## 5. K3 — 정상 실행 한 건을 정확히 평가

수정: `tests/live_context_evaluation.py`(또는 집계 함수를 scripts로 옮기고 이 파일은 얇은 CLI로 유지), 전용 집계 테스트.

- generated_at를 timezone-aware datetime으로 파싱한다. 요청한 KST 날짜의 `[00:00, 다음 날 00:00)`를 UTC로 바꿔 비교한다. 문자열 비교를 사용하지 않는다. naive/손상된 시각은 '시간 미확인'으로 따로 센다.
- `--run-id <GITHUB_RUN_ID-GITHUB_RUN_ATTEMPT>`를 추가한다. audit의 run_id·started_at/KST 범위를 맞춰 고르고, attempt_id 중복은 재차 세지 않는다. 다른 실행 파일은 제외 수를 보고한다.
- run의 성공/실패·event·mode·checkout SHA는 GitHub 실행 증거에서 별도로 확인한다. audit만으로 정상 일간 실행 여부를 추정하지 않는다. 평가 보고서에 증거 링크를 남긴다.
- 실행별 결과는 그 실행의 audit 및 실제 CTX 연결로 집계한다. 현재 candidate_context_state 전체의 상태는 `현재 대기열`로 따로 보여 주며 과거 실행 결과로 사용하지 않는다.
- 요청 수는 audit의 실제 requests_sent 합과 해당 실행의 context 보고를 비교한다. model_budget 일간 합계에는 같은 날 다른 실행이 들어갈 수 있음을 반영한다. 그 둘이 원래 같아야 한다고 단정하지 않는다.
- 같은 날 여러 검증기 버전이 있으면 버전별로 보여 준다. 현재 PARSER_VERSION과 다르다는 이유로 실제 해당 실행의 초안을 집계에서 없애지 않는다.
- audit가 없거나 truncated이면 불완전 증거로 보고한다. `raw_response`가 상한 처리로 dropped 객체가 된 경우에도 조용히 '원응답 있음'으로 세지 않는다. null code_sha와 문자열이 섞여도 집계가 예외를 내지 않게 한다.
- 날짜가 자정을 넘는 실행은 일자 집계와 run 집계를 구분하고, 요청·예산의 차이가 있으면 관련 attempt와 시각을 노출한다. 날짜를 조작해 합계를 맞추지 않는다.

필수 시험: 위 4개 UTC 경계, KST 자정 직전/직후, 다음 날 자료 제외, 같은 날 두 run과 attempt 중복, 구버전 초안, 현재 state의 후속 변경, 누락/잘린 audit와 null SHA. 테스트는 임시 파일만 쓴다.

I3-2 완료 시에는 수용 문장 전체와 최대 6기업을 원문 대조한다. MPC/PBF처럼 숫자가 맞더라도 세액공제·비현금 이익·보험 회수 같은 중요한 한계가 빠졌다면 **기계상 핵심 초안**과 **연구에 바로 쓸 수 있는 설명**을 구분한다. local 평가의 '핵심 2건'을 검토 완료된 원인 설명 2건으로 바꾸지 않는다.

## 6. K4 — 저장 결과만으로 비교표를 고친다

수정: `scripts/local_context_benchmark.py`, `tests/test_local_context_benchmark.py`, 작은 채점 fixture, J 평가 문서의 후속 절.

### K4-1. 판정과 집계

- manual_review의 값을 `{verdict, severity, reason, evidence, reviewed_at}`로 확장한다. 이전 문자열 correct/wrong은 호환하되 severity는 미지정으로 둔다. 이번 NBR 판정은 근거와 함께 critical로 명시한다.
- critical_accepted는 자동 규칙과 수동 critical 판정의 **주장 단위 합집합**이다. 같은 주장에 규칙 여러 개가 걸려도 오류 주장 한 개로 센다. 중대 오류 생성/거부 수에 단순 규칙 수를 빼서 음수가 나게 하지 않는다.
- metric/figure 일부가 맞는다는 이유만으로 correct로 확정하지 않는다. 정답표에 있는 subject, period, kind, GAAP, 수치와 지표의 관계를 같이 검사한다. 여러 figures 중 한 개만 일치하고 다른 수치가 틀리면 정답으로 세지 않는다.
- 원문 대조에 필요한 정답 정보가 없으면 unreviewed다. 표본 확대 없이 없는 정답을 추정하지 않는다. 정확도에는 검토 범위와 미검토 수를 함께 공개한다.
- 회수율도 올바른 지표·기간·주체와 연결된 사실만 센다. 단순 문자열 언급률이 필요하면 다른 지표로 표시한다. 반대 근거는 생성 단계와 검증 후 실제 표시 가능 단계의 회수율을 구분한다.
- 실패/not_run/dataset_missing 행에도 case의 split/group을 보존한다. 실패를 eval 분모에서 빼서 성공률을 높이지 않는다. schema 검사는 JSON 문법과 구분하고 타입·배열 길이·enum·필수 필드를 실제로 검사한다.

### K4-2. 검증기 버전과 재현성

- 기존 raw response, v4 당시 validation과 결과는 보존한다. v5/v6 등 후속 재검증은 새 평가 디렉터리에 쓰며 입력·모델 digest·prompt·실행 시 검증기·재검증 버전·채점 버전을 표시한다.
- 현재 report는 저장된 validation을 읽을 뿐 새 validator를 자동 적용하지 않는다. 명시적인 **오프라인 revalidate 명령**을 추가하거나 동일 목적의 작은 함수/CLI를 만든다. 보고서 재생성이 재추론을 유발하면 안 된다.
- 검증기만 달라졌다면 응답을 다시 생성하지 않고 저장 answer를 다시 검증한다. 실제 추론의 재개 키와 재검증 키를 분리한다. 같은 label에서 설정 변경 시 이전 raw 결과를 덮어쓰지 않는다.
- 개발/eval 경계는 보존한다. NBR 등 eval에서 발견한 결함을 반영한 결과는 '기존 표본에 대한 회귀 재검증'이라고 표시한다. 독립 성능 측정으로 바꾸지 않는다.
- Gemini 비교는 새 정상 실행의 문서·블록·prompt·FY가 같은 A군에 한한다. 일치 쌍 수와 제외 이유를 공개하고, 양쪽에 같은 검증기/채점 기준을 적용한다. 비교 자료가 없으면 미판정 유지.

필수 채점 시험: NBR 수동 critical가 자동 JSON/Markdown 모두 1, 수동/자동 중복은 1, 기간·주체·추가 수치 오류가 correct/recall을 높이지 않음, 미실행 eval도 분모 보존, 구버전 결과 보존, 오프라인 revalidate 동안 네트워크/모델 호출 0.

이번에는 저장된 20응답과 안정성 4응답만 재검증한다. 새 local/Gemini/SEC 요청으로 점수를 올리지 않는다. 원문 초안 보류 판정은 유지하며, 좁은 번역 시험은 I3-2 결과를 본 뒤 별도 목적·새 표본으로 설계한다.

## 7. K5 — 시험 서버 정리

새 실추론 계획이 없으므로 시험용 서버를 상시 켜 둘 이유가 없다. 구현 담당자가 다음을 수행한다.

1. 현재 11434 listener와 executable/command line을 다시 확인한다. 예전 PID 29036을 그대로 사용하지 않는다. 다른 사용자 작업이 진행 중인지 확인한다.
2. J 시험용 `ollama serve`로 확인되고 활성 요청이 없으면 해당 프로세스만 종료한다. 포트 종료와 GPU 모델 해제를 확인한다. 무관한 프로세스나 GitHub 타이머를 종료하지 않는다.
3. 이번 설치가 추가한 Startup/Ollama.lnk는 백업한 뒤 로그인 자동 실행에서 제외해 수동 실행을 기본으로 둔다. 이미 사용자 지시로 다른 용도에 쓰이는 항목이면 유지하고 보고한다. 시스템 시작 프로그램 전체를 바꾸지 않는다.
4. 모델 파일·로그인 정보·실험 결과는 삭제하지 않는다. cloud off/loopback 환경은 유지한다. 수동 재시작 명령과 복구 방법을 인수인계에 기록한다.

서버를 끄더라도 현재 GitHub의 Gemini 자동 운영에는 연결돼 있지 않아 영향이 없다. PC 타이머는 기존대로 자연 실행을 관찰한다. 전원 꺼짐을 해결하려고 PC 전체 절전/종료 정책을 바꾸지 않는다.
