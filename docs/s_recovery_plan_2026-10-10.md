# S 실행 계획 — 당일 복구와 발굴 품질 확인

작성: Codex, 2026-10-10 KST. 구현 담당자: Claude.

## 판단과 근거

사용자 검토를 반영한 확정 순서: S0-A 부분 성공 시 위험 알림 허용 → S0-B 당일 자동 복구. S3 후보 8개 평가는 S0와 병행해 즉시 시작한다. S1은 남는 예산으로 여러 날에 나눠 진행하고 S2는 각 변경의 운영 반영 직후부터 관측한다. 기존 Q/R 수정은 반복하지 않는다.

STATUS의 10/10 인수인계에 따르면 10/7~10/10 추출 장애로 notify가 차단됐다. 사용자 보완에 따르면 10/9에는 9건이 정상 처리됐지만 일부 실패로 notify가 차단됐다. 이전 문서의 '10/9 추출 성공'은 단계 전체 성공을 뜻하지 않으므로 정정한다. 모든 종류의 알림 중단도 아니다. 같은 기록에 PBF material_update 10/9 발송이 있다. 기본 수집 파일이 없는 재실행 문제는 이미 수정됐으므로 재구현하지 않는다. thinking 사용과 503의 인과는 작은 표본으로 확정할 수 없다.

직접 읽은 코드에서 commands 계획은 즉시 빈 결과를 반환한다. extract의 일반 요청 실패는 항목별 next_retry_at을 12시간 뒤로 잡는다. 따라서 공용 503 대기가 끝나더라도 항목 대기 때문에 바로 복구되지 않을 수 있다. 두 시계를 함께 다뤄야 한다.

위 운영 결과는 인수인계와 사용자 관측이며 이번에 원격 실행을 다시 조회한 결과는 아니다. 수정 시작 시 git status에서 STATUS 수정과 이 계획 문서 미추적 상태를 확인했다. 두 문서는 아직 커밋하지 않았다.

## S0-A — 부분 성공이면 확인된 위험 알림 허용 (첫 구현)

수정 대상: scripts/extract.py, scripts/daily_run_state.py, 기존 추출·단계·notify 시험, README. notify 자체의 종목·근거·중복 발송 필터는 유지한다.

- 현재 extract는 failed > 0이면 degraded 기록과 종료 코드 1을 함께 반환한다. notify는 extract의 execution_status=success를 요구한다. 이 결합을 수정한다.
- 당일 검증된 처리 결과가 있고, 미완료 사유가 503/공용 과부하 대기뿐이며, 신호와 대기 원장이 정상 저장됐으면 종료 코드 0, execution_status=success, quality_status=partial로 기록한다. 정상 처리에는 근거 검증을 마친 채택 또는 정상 비신호 판정이 포함된다. 단순 사전 필터 제외나 근거 검증 실패를 모델 처리 성공으로 세지 않는다.
- extract 품질 probe를 추가하고 현재 run_id에 연결된 완료 기록만 읽는다. 처리·채택·거절·503·대기 건수와 사유를 분리한다. 자료 부족을 complete로 표시하거나 '위험 없음'으로 해석하지 않는다. notify는 기존 원장 안의 검증된 유효 위험 신호만 읽는다. 알릴 신호가 없으면 0건으로 끝난다.
- 같은 날 재개가 전부 503이어도 그날 앞선 실행에서 저장된 유효 결과가 있으면 partial을 유지할 수 있다. 현재 날짜·수집 입력과 연결된 저장 증거로 판단하고 이전 날짜 결과를 당일 처리로 세지 않는다. 그날 유효 처리 0건인 전면 실패, 인증/429 차단, 원장 손상·저장 실패·미분류 오류는 이 예외로 성공 처리하지 않는다.
- 원문 유효기간 14일 내 재처리 대상으로 미완료 항목을 보존한다. 기간 내 처리 성공은 보장하지 않으며 만료된 항목은 만료 사유와 수를 남긴다. 부분 성공은 미처리 위험 신호까지 발견했다는 뜻이 아니다.
- 필수 시험: 9건 정상+1건 503에서 partial 및 notify 실행 가능, 정상 0건+503은 차단, 당일 partial 후 전부 503 재개, 전날 성공만 있는 경우 차단, 원장 저장 실패 차단, 오래된 run_status 오인 방지, partial 후 재개 및 동일 신호 중복 발송 방지. 가짜 전송만 사용한다.

## S0-B — PC 없이 같은 날 복구

수정 대상: scripts/daily_run_state.py, scripts/extract.py, 공용 모델 대기 함수가 있는 scripts/common.py, config/research_policy.json, .github/workflows/daily_discovery.yml, tests/test_daily_run_state.py, tests/test_model_budget.py 및 기존 추출 시험. README에 동작 변경을 설명한다.

1. 명시적 commands 실행은 명령 처리 전용으로 유지한다. 6시간 예약 실행에만 제한된 복구 계획을 추가한다. 새 모드 또는 명시 플래그로 구분하고 계획·종료 판정에 같은 구분을 적용한다. 단순히 모든 예약을 auto로 바꾸지 않는다.
2. 입력은 현재 KST 날짜의 일간 단계 기록, 단계 실패 원인, 모델 공용 대기/차단, 항목별 next_retry_at, 남은 모델 예산이다. 오늘 일간 기록이 없으면 복구하지 않는다. 성공한 독립 수집·스크리닝을 다시 실행하지 않는다.
3. 최초 범위는 모델 일시 장애로 실패하거나 success/partial로 남은 extract와 기존 context 초안 재개다. 재시도 시점이 된 미완료 항목을 확인해 원인 단계와 기존 의존 관계상 그것을 사용하는 단계만 계획한다. partial을 success라는 이유로 복구 대상에서 누락하지 않는다. blocked 단계만 단독으로 실행하지 않는다. context 재개는 저장 문서만 쓰고 SEC 요청은 0이다.
4. 복구는 날짜별 최대 2회, 이전 복구 시작에서 최소 60분 간격이다. 실제 비어 있지 않은 계획을 저장할 때 사용량을 먼저 영속 저장한다. 재시작으로 카운터를 초기화하지 않는다. 공용 대기·항목 대기·일일 예산 중 하나라도 막으면 모델 복구를 계획하지 않고 사유를 남긴다. 기존 draft_resume_max·partial_retry_max와 각각의 제한도 동시에 적용한다.
5. 503은 항목의 내용 오류와 구분해 기록한다. 항목 재개 시각은 기존 공용 과부하 대기 정책을 따르고, 공용 대기가 연장되면 그 시각도 존중한다. 429와 인증 오류는 이 경로로 우회하지 않는다. 과거 HTTPError만 기록된 항목은 503이라고 추측해 대기를 줄이지 않는다. 날짜 전환도 기존 제공자 차단 규칙을 따른다.
6. 기본 raw 파일이 없어도 저장된 대기 항목으로 재개하는 수정은 유지한다. 명시 경로 누락은 오류다. 미처리 항목이 남으면 complete로 판정하지 않는다. notify 허용 여부는 S0-A의 당일 유효 결과와 오류 분류 기준을 따른다.
7. 출력에는 복구 이유, 대상 단계, 실행/일간 누적 횟수, 남은 대기 사유, 처리/대기 건수를 기록한다. 의존 단계가 실패하면 복구 실행도 성공으로 표시하지 않는다. 기존 단일 작성자·발송 예약·uncertain 잠금·상태 저장 규칙을 유지한다.

완료 기준: 가짜 시계·가짜 모델로 PC 없는 예약 재개, 대기 중 0요청, 429 차단, 항목 12시간 대기와 503 대기의 분리, 하루 2회 누적 제한, 재시작·KST 경계, 일간 기록 없는 날, raw 없는 체크아웃, 의존 단계 차단을 검증한다. 실제 발송은 하지 않는다.

일정 한계: 사용자 관측상 일간은 약 15시 KST, 이후 21:23 예약은 약 22:30에 시작해 당일 실제 복구 기회가 보통 1회다. '최대 2회'는 상한이며 두 번 실행 보장이 아니다. cron 지연으로 자정을 넘으면 당일 복구 기회가 0회일 수도 있다. 이번에는 예약 빈도를 늘리지 않는다. S0-A로 이미 확보한 위험 신호를 전달하고 S0-B로 누락을 보완한다. 합성 일정 시험에 15시→22:30 1회와 자정 지연을 포함하고 실제 복구 기회 수를 관측한다.

## S1 — 추출 thinking 변경은 품질 비교 후 결정

S0와 별도 커밋으로 진행한다. 우선 기존 설정을 유지한다. 비교 대상으로 thinkingBudget=0을 설정값으로 지원하되 운영 기본값은 평가 전 바꾸지 않는다. 503 재시도에서 조용히 모드를 바꾸는 방식은 채택하지 않는다.

수정 대상: scripts/extract.py, config/research_policy.json, 추출 시험, data/eval/s_2026-10-10/ 평가 자료. 모델 설정·실제 사용 설정·prompt_version을 결과와 연결한다. 버전 변경으로 accepted 항목이 재등록되거나 대기 항목의 사용 이력이 초기화되지 않게 한다.

저장 원문 12개를 먼저 고정한다: 실제 전망 변경 3, 확정 실적/전망 유지 3, 회사 식별·기간 혼동 3, 비신호 3. 원문에서 기대 판정을 수작업으로 기록한다. 네트워크 없는 검증은 즉시 진행한다.

모델 비교는 최소 24회가 필요하다. 내부 정책의 20회와 제공자의 실제 프로젝트·모델별 할당량은 별개다. 실제 한도·초기화 시각은 호출 전 프로젝트 콘솔/공식 자료로 확인해 평가 기록에 남긴다. 확인 전에는 무료 한도=20회 또는 태평양 자정 초기화를 확정 사실로 사용하지 않는다.

- 하루 최대 원문 1개×두 설정=2회, 최소 12개 평가 가능일에 나눠 진행한다. 실패 요청도 2회 상한에 포함하고 당일 즉시 재시도는 하지 않는다. 표본 순서는 고정하고 설정 선후는 번갈아 배치한다.
- 당일 운영·예정 복구가 끝나고 운영 대기 작업이 없으며 공용 예산과 extract 몫 모두 2회 이상 남을 때만 한 쌍을 시작한다. 평가도 동일 예산 원장에 요청 전에 기록한다. 제공자 한도·대기와 로컬/CI 공유 사용량도 확인한다. 별도 프로세스로 예산을 우회하지 않는다.
- 운영이 20회를 모두 사용하거나 추출 몫이 남지 않으면 평가 0회다. 따라서 12일은 달력상 완료 약속이 아니다. 운영 몫은 줄이지 않는다. 3일 연속 여유가 없으면 '가용 예산 없음'으로 기록하고 오프라인 결과만 보고한다. 별도 평가 프로젝트/예산 확보는 후속 선택지로 남기며 자동 전환하지 않는다.
- 한 설정이 503이면 다른 설정의 성공과 단순 성공률 비교를 하지 않는다. 실패도 보존하고, 불완전한 쌍은 다음 평가 가능일에 두 설정을 다시 비교한다. 첫 시도 시작 후 21일에 중간 결산하며 12쌍 미완료면 설정 변경을 보류한다. 운영 복구·S3·S2는 기다리지 않는다.

같은 입력의 기존/0 설정 결과를 비교해 회사·기간·전망/실적·수치·인용 오류와 정상 신호 누락, HTTP 실패·지연을 별도로 보고한다. 중대한 근거 오류 0건, 기존 정답의 추가 누락 0건을 통과 기준으로 삼는다. 두 설정이 모두 틀린 항목도 실패로 기록한다. 작은 표본의 성공률을 공급자 안정성 입증으로 표현하지 않는다. 미통과 시 기존 설정 유지, 통과 시 새 버전으로 적용하고 이전 설정을 복귀값으로 남긴다.

## S2 — 배포 후 운영 확인

구현 검증은 무시 파일 없는 임시 복제본에서 전체 unittest, 기존 Q/R 재현, Linux·Windows·날짜 시나리오 CI로 한다. 수정 전/후 증거를 분리하고 SHA·시험 수·설정을 인수인계에 남긴다. 배포와 외부 실행은 별도 작업 범위로 기록한다.

각 변경의 운영 반영 직후부터 정상 일간 3회와 실제 일시 장애 후 자동 재개 1회를 관측한다. S1 평가 완료를 기다리지 않는다. partial 때 notify 실행 가능 여부·실제 발송 적격 신호·영수증·미완료 건수를 함께 확인한다. 적격 신호가 없으면 0건이 정상이며 발송을 유도하지 않는다. 장애가 없으면 재개는 합성 시험 통과/운영 미관측으로 남긴다. 실행 ID·SHA·모델 요청 수·대기열 감소·단계 상태·발송 영수증으로 판정한다. 시험 통과만으로 복구 완료라고 쓰지 않는다. 확인용 수동 전체 실행이나 시험 알림은 하지 않는다.

Q/R 중 이미 관측된 PBF 발송과 v3 백업은 다시 과제로 열지 않는다. CLBK 새 초안·folded 초안 몫은 미관측 항목으로 별도 추적한다.

## S3 — S0와 병행해 후보 8개 즉시 평가

대상은 사용자가 제시한 10/6 이후 화면 기반 알림 후보 SPCX, BP, JXN, VSEC, DHT, FRO, INSW, PBF다. S0 완료를 기다리지 않고 저장 카드·원문·알림 영수증을 읽어 시작한다. 첫 산출물은 docs/s_candidate_value_review_2026-10-10.md이며 구현 담당자의 첫 인수인계에 8개 모두의 확인/미확인 표를 포함한다. 모델 호출 없이도 진행한다. 동일 체크아웃의 동시 쓰기나 하위 에이전트 사용을 뜻하는 병행은 아니며 코드와 연구 산출물을 독립적으로 진행한다.

실제 발송일·당시 카드 버전·회사 식별자를 먼저 대조한다. 특히 티커만으로 회사를 추측하지 않는다. 알림 당시 알려진 근거와 이후 추가된 정보를 분리한다. 회사가 돈 버는 방식, 회사 규모 대비 이익 변화, 시장 예상과의 차이, 지속 근거, 반증 조건을 같은 표로 정리한다. 원문이 부족하면 미확인으로 둔다. 같은 업종·공통 원출처는 독립 근거 여러 개로 세지 않는다. 그중 다음 조사 가치가 높은 최대 3개와 필요한 원문·지표를 제안하며 기준 미달이면 3개를 채우지 않는다. 이는 발굴 품질 검토이며 미추적 후보의 심층 검증이나 자동 추천 승인·원장 변경·전송은 포함하지 않는다.

성과는 최초 통과/카드/알림 기준을 그대로 분리하고 평가 기간이 찬 표본만 계산한다. 수익률이 아직 없으면 근거 정확도와 추가 연구 가치를 평가한다. 새 출처·화면·모델 확대는 이 결과에서 드러난 결손을 근거로 다음 계획에서 정한다.

## 범위와 인수인계

이번 계획의 개발 범위는 부분 성공을 통한 위험 알림 허용, 복구 경로와 설정 평가다. 후보 8개 연구 가치 평가는 독립 산출물이다. 예산 증액, 전체 수집 재실행, 과거 원장 소급 변경은 제외한다. 연구 성과와 운영 성공을 구분한다.

각 단계 완료 시 수정 파일·커밋·입출력 예시·합성 시험 결과·운영 관측/미관측·남은 문제를 STATUS와 S 인수인계에 남긴다. 이번 Codex 작업은 계획 문서와 STATUS 갱신이며 코드 구현·테스트 실행·모델 호출·원장 수정·외부 전송은 수행하지 않았다.
