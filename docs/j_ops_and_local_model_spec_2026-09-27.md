## 2. J1 — 실제 초안 평가와 재현 자료

### J1-1. 검증 전 입력·응답을 남긴다

대상: `scripts/candidate_context.py`, 필요 시 작은 전용 보조 모듈, 관련 테스트. 현행 `reports/generated/`는 일간 workflow가 이미 30일 아티팩트로 보관하므로 별도 배포 구조를 만들지 않는다.

현행 `excerpt()`는 거부 항목에서 metric/period/kind/subject/gaap를 버리고 인용을 자른다. 이 때문에 같은 거부를 완전히 재현하지 못했다. 운영 카드/CTX 스키마를 확장하는 대신 다음 **검증 전 응답 사본**을 `reports/generated/context_audit/<KST일자>/<attempt_id>.json`에 저장한다.

- schema_version, attempt_id, candidate_id, ticker, issuer 식별 정보, eps_target_period, run_id, 코드 SHA.
- provider/model, prompt_version/parser_version, 시작/종료 UTC 시각.
- document_ids와 각 원문의 SHA256, 실제 사용한 block_id/본문, source_coverage, 정확한 prompt와 prompt SHA256.
- 성공 시 **validate_draft에 넣기 전 answer 전체**와 검증 결과. 허용·거부 항목의 원래 필드를 그대로 보존한다. 정답을 보충하거나 거부 내용을 교정하지 않는다.
- 실패 시 예외 종류와 확인 가능한 HTTP 상태, 예산 전후 값. 키·헤더·.env·전체 예외 URL은 저장하지 않는다.
- 응답 JSON 파싱 이전의 원문이 호출 인터페이스에서 제공되지 않는다면 `raw_response_available=false`로 기록한다. 원응답을 얻으려고 재요청하거나 대규모 extract 리팩터링을 하지 않는다.

파일은 원자적으로 저장하고 attempt별로 구분한다. 파일당 512 KiB 상한을 두며 넘으면 원본 hash/크기와 `truncated=true`를 명시한다. 잘린 사례는 완전 비교에서 제외한다. 이 파일 저장 실패가 유효한 초안의 처리까지 중단시키지는 않되, 요약에 `audit_write_failed`를 남기고 그 실행을 재현 가능하다고 보고하지 않는다. 기존 모델 호출 수·재시도·하루 예산·카드 내용·알림 동작은 바꾸지 않는다.

필요한 테스트: 거부된 항목의 지표/기간/종류 보존, 입력 hash 재현, 성공/실패 감사 파일, 파일 상한, 감사 저장 실패 시 본 처리 유지, 비밀정보 부재, 기존 요청 수 불변. CI는 가짜 응답만 쓴다.

### J1-2. 정상 일간 실행 뒤 I3-2 평가

`docs/i3_live_evaluation_<실제일자>.md`에 실행 URL, 실제 체크아웃 SHA, KST일자, 자료 경로를 남긴다. 이벤트 head_sha만으로 실행 코드를 단정하지 않는다(워크플로는 실행 시 브랜치를 checkout한다).

1. 일간 단계 완료와 context 단계 결과를 각각 확인한다. 명령 전용 실행이나 context_verify를 정상 일간 실행으로 세지 않는다.
2. `model_budget.json`의 candidate_context 차감, 실제 요청, 저장된 응답/실패 수를 맞춘다. 일간 전체 20회와 원문 초안 6회 한도는 유지한다.
3. 기업별 상태를 집계한다: draft_ready, insufficient_earnings_context, no_supported_claims, failed, deferred_budget/provider_rate_limited. 대상 0·요청 0과 '요청했지만 0건'을 구분한다.
4. 수용 문장 수와 핵심 초안 수를 따로 센다. 수용된 기업 최대 6개를 **저장된 전체 원문**과 대조한다. 숫자·단위·기간·지표·귀속 주체·GAAP, 전망/실적 구분, 일회성·반대 근거, 근거 없는 인과관계가 없는지 확인한다.
5. 이전 failed/deferred 기업의 처리 순서와 새 기업의 대기 여부를 확인한다. 같은 실패 기업 반복 때문에 발굴 범위가 줄어들면 구체적 큐 순서로 보고한다.
6. 0건이면 제공자 실패, 호출 예산/시간, 원문 부적합, 발췌 누락, 모델 형식/내용 오류, 검증기 과잉 거부로 나눈다. 없는 원응답은 추정하지 않는다. 실제 반례가 있는 원인에 한해 **한 차례 표적 수정+회귀 테스트**를 한다. 숫자·주체·기간 검증을 전체적으로 완화하지 않는다.

정상 실행이 아직 없으면 `운영 대기`, 원문 대조 없이 검사만 통과했으면 `기계 검증만 확인`, 실제 유용한 초안이 확인됐으면 표본 수와 한계를 함께 적는다. 0건인 결과도 숨기지 않는다. 보존 기능 배포 전에 실행됐다면 얻을 수 있는 범위만 평가하고 다음 정상 실행을 기다린다.

## 3. J2 — PC 타이머의 실상 확인

대상은 저장소 밖 `%USERPROFILE%\.research-timer\dispatch.ps1`, 예약 작업 두 개와 해당 로그다. token.txt의 내용은 출력·복사·커밋하지 않는다.

2. 9/26 22:29:58의 로그와 GitHub workflow_dispatch 실행을 대조한다. 앞선 인수인계의 'dispatch 없음'을 정정하되, 로그 `ok`만으로 어떤 run이 성공했다고 단정하지 않는다.

4. 설정/경로/조건의 명백한 오류면 해당 두 작업과 스크립트를 먼저 백업한 뒤 필요한 값만 보완한다. 전원 정책 전체 변경, 관리자 권한 확대, 자격증명 교체는 이 작업의 기본 해법으로 삼지 않는다. PC가 꺼져 있던 것이 원인이면 GitHub 대체 실행의 실제 지연을 보고하고 '항상 정시'를 약속하지 않는다.
5. 변경 검증은 요청을 보내지 않는 점검 모드와 다음 예정 실행의 로그 대조로 한다. `Start-ScheduledTask`나 dispatch 스크립트를 시험 삼아 실행하면 명령 응답/알림이 발생할 수 있으므로 하지 않는다.

산출물: `docs/j_timer_diagnosis_2026-09-27.md`. 원인(확정/추정), 변경 전후, 백업 위치, 다음 자연 실행에서 확인할 항목을 적는다. 토큰 경로 외의 비밀값, 계정 SID 등 불필요한 개인정보는 넣지 않는다. 점검 스크립트를 저장소에 추가하면 읽기 전용 기본값을 갖게 한다.

## 4. J3 — Ollama 로컬 모델을 실제 연구 자료로 시험

### J3-1. 설치와 격리

첫 모델은 **`qwen3.5:9b` Q4_K_M**, Ollama 공식 배포본을 사용한다. 조회 시 모델 파일 약 6.6GB이며 실제 메모리 사용은 별도다. 설치/다운로드 전 디스크 20GB 정도의 여유와 GPU 상태를 확인한다. 모델은 저장소·OneDrive 밖 기본 모델 디렉터리에 둔다. 다운로드/설치는 허용되며, 모델을 여러 개 모으거나 GPU 드라이버를 임의 교체하지 않는다.

- 실행 시 `127.0.0.1:11434`에만 연결. 인증·터널·포트 포워딩·GitHub 연결은 구현하지 않는다.
- `OLLAMA_NO_CLOUD=1`, 동시 추론 1개. 이미 실행 중인 Ollama가 있다면 설정을 확인하고 무관한 세션을 종료하지 않는다. 직접 시작하는 백그라운드 프로세스는 `Start-Process -WindowStyle Hidden`을 사용한다.
- 설치 버전, 모델 전체 digest/tag, 양자화, NVIDIA 드라이버, 실제 GPU/CPU 분배를 기록한다. 태그 이름만으로 재현성을 주장하지 않는다.
- 초기 설정: num_ctx=16384, num_predict=3072, temperature=0, seed 고정, stream=false, think=false(해당 모델의 API 지원을 확인). JSON schema로 응답 구조를 제한한다. 원문 정확도는 현행 v4와 별도 대조표로 검사한다.
- 메모리 부족/지속 CPU offload/시간 초과는 환경 결과로 기록한다. dev 표본에서 설정 조정은 한 번까지만 하고 최종 설정을 고정한다. 모델 변경·원문 발췌 변경은 새로운 실험으로 분리한다.
- 모델 설치·pull 외의 연구 입력용 외부 통신은 하지 않는다. 클라이언트는 프록시를 우회하는 loopback 전용 연결을 쓰고 리다이렉트/원격 호스트를 거부한다.

### J3-2. 수정 파일과 실행 인터페이스

추가할 파일(이 이름을 기본으로 사용):

| 파일 | 책임 |
|---|---|
| `scripts/local_context_benchmark.py` | prepare/run/report 명령, 표준 라이브러리 HTTP 클라이언트, 원응답/계측/검증 결과 저장 |
| `tests/fixtures/local_context_benchmark/manifest.json` | 공개 원문 ID·block ID·hash·20개 사례 정의와 dev/eval 구분 |
| `tests/fixtures/local_context_benchmark/review_labels.json` | 원문 대조 기대 사실·중대 오류 조건·중요 근거 목록 |
| `tests/test_local_context_benchmark.py` | 가짜 로컬 서버와 격리/오류/재개 시험 |
| `docs/j_local_model_evaluation_2026-09-27.md` | 환경, 실행 명령, 비교표, 채택 판단, 미검증 범위 |

기존 `relevant_blocks`, `draft_prompt`, `validate_draft` 순수 함수를 재사용한다. **`run_sources`, `run_drafts`, `store_context`, 카드 생성·원장 갱신 함수를 시험에서 호출하지 않는다.** 운영 provider 전환 계층과 자동 fallback은 이번에 만들지 않는다.

도구 인터페이스:

```text
python scripts/local_context_benchmark.py prepare --source-data <고정한_운영자료_사본> --manifest <manifest.json> --output <실험폴더>
python scripts/local_context_benchmark.py run --experiment <실험폴더> --model qwen3.5:9b --endpoint http://127.0.0.1:11434 --resume
python scripts/local_context_benchmark.py report --experiment <실험폴더> --labels <review_labels.json> --output <보고서경로>
```

`prepare`와 `report`는 네트워크 요청을 전혀 하지 않는다. 출력 기본값은 `reports/generated/local_model/<experiment_id>/`이며 data/processed, data/raw, config, 추적/발송 원장을 출력 경로로 허용하지 않는다. 실행 환경에서 API/텔레그램 키를 넘기지 않고, `.env`를 읽는 함수를 사용하지 않는다. RESEARCH_DATA_DIR 하나만 바꾸고 전체 파이프라인을 실행하는 방식은 허용하지 않는다.

실험 manifest에 입력 사본 SHA를 고정한다. 각 요청의 정확한 prompt/blocks/schema, model 설정, JSON 파싱 전 원응답, 파싱된 응답, v4 검증 결과, 오류/시간/토큰 통계를 파일에 남긴다. 실패도 결과 한 건이다. 재개는 **입력·모델 digest·설정·prompt·검증기 버전이 같은 완료 항목만** 건너뛴다. 운영 CTX/OB/CAN 기록과 섞이지 않는 실험 ID를 사용한다.

### J3-3. 20개 사례 구성과 정답표

**10문서를 이용해 20사례**를 만든다. 원문·문장 내용을 인위적으로 바꾸지 않는다.

- A군 10개: 기업마다 현행 함수가 고른 전체 발췌와 현행 prompt를 그대로 사용한다. 실제 초안 생성에 얼마나 쓸모 있는지 평가한다.
- B군 10개: 같은 기업에서 좁은 근거 구간을 골라 숫자/지표/기간/주체 연결과 근거 부족 시 답하지 않는지를 평가한다. 발췌가 다르므로 A군과 분리 집계한다.
- AMCX/AEHR의 A·B 총 4개는 dev, 나머지 16개는 eval로 고정한다. 모델 출력을 보기 전에 사례와 정답표를 확정한다. eval을 보고 prompt/검증기를 조정하면 결과를 개발 결과로 표시하고 일반화 성능으로 보고하지 않는다.
- PBF 연결/귀속 순이익, AMCX 영업/조정 영업이익, AEHR 전망 범위, TALO 산업 단위, MPC 자회사 배당, DK 머리글 없는 표, 기간 불명/인과 미확인을 포함한다. 표본에 없는 현상은 억지로 만들지 않는다.
- 각 사례에 원문 위치, 허용되는 핵심 사실, 잘못 연결하면 중대 오류인 항목, 중요한 반대 근거, 충분한 근거가 있는지, 입력에 그 근거가 실제 포함됐는지를 기록한다. 정답은 원문 대조로 정하고 모델 답변을 정답으로 삼지 않는다.
- 원문 누락/손상/hash 불일치는 `dataset_missing`으로 끝내며 SEC에서 다시 받지 않는다. 실제 확보 사례 수를 분모로 공개하되, 적은 표본으로 원래 20개 기준을 통과했다고 보고하지 않는다.

### J3-4. 실행 한도·오류 처리·비교 원칙

- 요청당 120초, 전체 추론 45분 상한, 동시 1개. 개발 중 버린 최대 2회 + 최종 20사례 + 고정 4사례 안정성 재실행까지 **총 26회 상한**. 결과를 보고 마음에 드는 응답이 나올 때까지 재시도하지 않는다.
- 예열/모델 로딩과 정상 추론 시간을 구분한다. 전체 응답 시간, prompt_eval_count, eval_count, eval_duration, 가능하면 peak VRAM을 기록한다. 측정 못 한 항목은 미측정으로 둔다.
- 연결 거절, timeout, OOM, 503, 비정상 JSON, schema 불일치, 출력 잘림을 구분한다. API가 `done_reason=length` 등을 주면 불완전 출력이며 성공으로 세지 않는다. 응답을 자동 수선해 통과율을 높이지 않는다.
- 추론 실패 뒤 클라이언트가 종료돼도 서버 작업이 남았는지 확인하고 무한 적체를 만들지 않는다. 512 KiB 응답 상한과 experiment별 결과 보존을 둔다.
- 기존 Gemini 저장본과 비교할 때 **같은 문서·블록·prompt·target FY**인 쌍만 paired로 표시한다. 프롬프트가 달랐던 v2 재구성 fixture를 Gemini의 실제 정답률로 취급하지 않는다.
- 새 J1 감사 자료가 같은 입력이면 v4로 동일하게 재검증해 비교한다. 같은 입력 자료가 없으면 로컬 절대 평가만 완료하고 'Gemini보다 우수/열세 미판정'으로 남긴다. 비교를 위해 Gemini를 추가 호출하지 않는다.

### J3-5. 지표와 채택 판단

기계 검증 통과와 실제 사실 정확도를 따로 보고한다. 개발/eval, A/B, 모델 간 동일 입력 비교 여부를 각각 구분한다.

1. 요청 성공률, JSON/schema 성공률, 시간 초과/메모리 실패 수.
2. 주장 수·기계 수용 수·원문 대조에서 맞은 수. **수용됐지만 틀린 주장**을 별도로 공개한다.
3. 핵심 초안이 가능한 사례 중 유용한 핵심 초안이 나온 비율. 근거가 없는 사례의 정당한 보류도 센다.
4. 정답표의 중요한 사실/반대 근거 회수율. 모델에 안 보인 근거의 누락(발췌 문제)과 보고도 놓친 근거(모델 문제)를 분리한다. '전부 빈 답변'은 높은 정확도로 채택하지 않는다.
5. 중대 오류: 지표·금액·기간·통화·귀속 주체·GAAP/전망 혼동, 원문에 없는 주장, 근거 없는 EPS 인과 확정. 기존 검증기가 놓치면 그 사례를 회귀 입력으로 남긴다.
6. warm 실행 시간 중앙값/p95, 모델 로딩 시간, 사용 가능한 경우 GPU 메모리. API 요청 비용 0과 전기/PC 점유 비용을 구분하며 측정하지 않은 전기비는 산정하지 않는다.

**초기 보조 도구 채택 기준**(투자 성과 기준이 아니며 작은 표본에 한정): eval에서 중대 오류가 기계 검증을 통과한 사례 0, JSON/schema 성공률 90% 이상, 원문 대조 기준 수용 주장 정확도 95% 이상, 입력에 있는 중요 근거 회수율 70% 이상, warm p95 120초 이내. 분모가 0이면 미평가이며 통과가 아니다. 4개 안정성 반복에서도 새 중대 오류가 없어야 한다. 기준에 미달해도 실험은 정상 완료할 수 있다.

최종 판정은 `보조 분석 시험에 사용 가능 / 번역·정리 등 더 좁은 범위로 추가 시험 / 현재 보류` 중 하나와 근거를 적는다. 이 시험은 원문 초안 평가이므로 번역 성능까지 검증했다고 쓰지 않는다. 통과해도 운영 연결·자동 추천·로컬 모델 단독 후보 탈락은 이번에 구현하지 않는다.

### J3-6. 의미 있는 검증

새 CI 테스트는 Ollama 설치·모델 다운로드·실추론 없이 가짜 서버로 실행한다. 최소 확인: 정상 응답, 잘못된 JSON/잘린 출력, timeout/OOM/연결 거절, 원격 endpoint 거부, 입력 hash 변경 후 잘못된 재개 방지, 모델/설정/검증기 변경 구분, 보존된 응답의 오프라인 재검증, 운영 저장 함수 호출 금지, 운영 원장 불변.

실제 로컬 시험 전후 고정 사본의 hash와 로컬 운영 파일 변경 여부를 비교한다. GitHub 정기 실행으로 원격 원장이 정상 변경되는 것과 로컬 시험이 파일을 쓴 것을 혼동하지 않는다. 새 도구 테스트와 전체 회귀·날짜 CI가 통과하면 불필요한 반복 실행은 하지 않는다.
