# Claude 변경사항 검토와 다음 구현 지시서

검토자: Codex · 2026-09-25. 비교 기준 `ff6231f` → 코드 `3e31b18`, 최신 운영 상태 `a342309`. 사용자 요청에 따라 이번 작업은 검토·설계·지시서 작성이다. 아래 수정 사항은 아직 구현하지 않았다.

## 1. 결론과 방향

사용자가 승인한 최신 목적은 **전 산업에서 시장이 충분히 반영하지 않은 이익 변화를 찾아 추적할 후보를 발굴하는 것**이다. ALAB·CRDO·MRVL 검증은 이 업무의 일부이며 전체 엔진의 중심이 아니다. 기존 세 기업 중심 설계보다 목적에 가까워졌다.

전 종목 EPS 상향 스크리너는 유용한 첫 번째 후보 생성기다. 그러나 컨센서스가 이미 움직인 뒤의 신호이므로 이것만으로 조기 발굴 엔진이 완성되지는 않는다. 가격·공급·수주·회사 전망 변화의 선행 신호가 다음 축이다. 상향 폭은 후보 선정 근거이며 시장 미반영·지속성의 입증을 대신하지 않는다.

우선순위: **데이터 누락과 상태 표시 수정 → 재실행·이력 보존 → 근거 있는 후보 카드와 추적 절차 → 선행 신호 확장 → 종목별 웹 화면**. 현재 규모에서 DB 이전·도메인 구매는 선행 조건이 아니다.

## 2. 확인한 변경과 검증 범위

- AGENTS/PRINCIPLES: 전 산업 발굴 우선, 후보의 이익 변화·시장 미반영·지속 근거를 평가하도록 전환.
- `screen_revisions.py`: SEC 상장 목록, Yahoo 시세·EPS 과거 제공값으로 A/B 후보 생성. 과거 제공값을 metric_log의 실제 과거 관측으로 위장하지 않는 분리는 유지됐다.
- 일간 워크플로: daily/auto/commands 분리, PC 타이머와 GitHub 예약 병행, SEC 연락처를 secret 우선으로 처리.
- 날짜별 압축 스냅샷과 Markdown 결과, 운영 상태에 스크리너 추가.
- 로컬 테스트 **72개 통과**. 원격 main의 추가 두 커밋은 명령 처리 운영 상태만 변경했고 fast-forward로 반영했다.
- Windows 작업 `Research daily run`, `Research command check`는 Ready 상태다. 이것은 예정 시각 실제 실행 성공이나 상시 PC 설치 완료를 입증하지 않는다.
- 이번 검토에서는 운영 수집·텔레그램 전송·새 배포를 실행하지 않았다. 외부 시장 수치와 급등 사례의 사실관계를 독립 재검증하지 않았다. Claude가 남긴 브라우저 확인 기록도 이번에 재실행하지 않았다.

## 3. 발견 사항 — 중요도순

### P1. 핵심 정보가 전부 빠졌는데 성공으로 기록됨

위치: `scripts/screen_revisions.py:285–311`, `data/processed/revision_screen/2026-09-25.json.gz`.

실제 저장 결과는 대상 3,238개, 점수 계산 2,267개, 후보 96개, 조회 HTTP 오류 322개다. **후보 업종 확보 0/96, 상위 중복 제거 31개 중 주가 비교 확보 0/31, 업종 묶음 0개**다. 그런데 run_status는 success다.

프로필과 주가 조회가 한 try 안에 있어 프로필 요청이 실패하면 주가 조회도 건너뛴다. 이 단계 예외는 집계하지 않는다. 322/3238은 약 9.94%라 현재 10% 기준에도 걸리지 않는다. HTTP 상태 코드가 없어 429 제한인지 다른 접근 오류인지는 확정할 수 없다. 로컬에서 업종 묶기가 됐다는 기록과 최신 운영 결과를 구분해야 한다.

### P1. 실패한 일간 실행도 당일 완료로 취급할 수 있음

위치: `.github/workflows/daily_discovery.yml:46–57`.

auto/예약 건너뛰기는 collect.checked_at 날짜만 확인한다. collect 자체가 failed여도, collect 이후 EPS·스크리너가 실패해도 같은 날 재시도 기회를 막는다. 수집 시도와 전체 일간 업무 완료는 서로 다른 상태다.

### P1. EPS 정의가 불완전해도 후보 계산을 허용함

위치: `scripts/screen_revisions.py:111–165`.

통화 None을 허용하고 fy_end 누락을 차단하지 않는다. 실제로 통화·대상 기간이 모두 없는 입력도 candidate=True가 되는 것을 순수 함수 호출로 재현했다. 종목 응답의 동일성, 유한한 숫자, 회계기준에 대한 검증도 충분하지 않다. 가격이 USD인 것만으로 EPS의 통화를 증명할 수 없다. 제공자의 +1y 과거값은 자체 관측이 아니며 기간 일관성을 검증할 수 없는 경우 별도 한계를 표시해야 한다.

### P2. 주가 비교의 조정 기준과 날짜가 맞지 않을 수 있음

위치: `scripts/screen_revisions.py:80–90`, `market_follow`.

과거에는 adjusted close를 우선 사용하고 현재에는 regularMarketPrice를 사용한다. 배당 조정 등이 섞이면 같은 가격 기준 비교가 아니다. 과거 거래 시각과 현재 시세 시각도 출력에 남지 않는다. 이 값으로 PER 변화를 계산하려면 동일 기준·대상 기간·확인 가능한 시점이 필요하다. 현 운영에서는 이 비교값 자체가 모두 비어 있어 수치 왜곡이 발생했다고 단정하지는 않는다.

### P2. 같은 날 스크리너를 재실행하면 이전 스냅샷을 덮어씀

위치: `scripts/screen_revisions.py:226–232,303`.

날짜만으로 파일명을 정한다. Git에 먼저 저장된 버전은 복구 가능하지만 커밋 전 재실행은 첫 실행 결과를 잃고, 실행별 분석도 어렵다. 원 응답 전체 대신 가공된 일부 필드만 남기므로 점수 재현과 오류 조사에도 제한이 있다. 실패 티커 목록도 없어 선택 재시도가 어렵다.

### P2. 발굴 결과가 사용자 행동으로 연결되지 않음

`notify.py`, `telegram_cmd.py`에는 새 스크리너 결과를 읽는 경로가 없다. 현재 결과는 Markdown/압축 파일이며 후보 알림, 한국어 설명, 추적 선택, 종목 페이지까지 연결된 상태가 아니다. 이것은 현재 단계의 미구현이지 기존 알림 전체가 고장났다는 뜻은 아니다.

### P2. 사례 근거와 에이전트 지침이 불완전함

`docs/surge_signal_cases_2026-09-25.md`는 정확한 수치를 적지만 개별 원문 URL을 비공개 화면에 맡긴다. 저장소만 받은 작업자는 검증할 수 없다. 또한 CLAUDE.md는 존재하지 않는 AGENTS의 4·6절을 참조하고 진입/보유/축소 표현을 별도로 요구한다. 최신 공통 범위와 충돌하므로 정리가 필요하다.

## 4. 구현 작업 A — 수집 품질과 실패 표시 (최우선, 별도 커밋)

대상: `scripts/screen_revisions.py`, `config/research_policy.json`, `tests/test_screen_revisions.py`, 필요 시 `scripts/gen_report.py`.

1. 각 티커의 결과를 success / unavailable / failed로 구분한다. unavailable은 정상 응답이나 분석가·기간·숫자가 부족한 경우이며 네트워크 실패와 섞지 않는다. 단계는 universe, quotes, earnings, profile, price로 구분한다.
2. 예외 기록은 stage, ticker, error_type, http_status, attempts, retrieved_at만 남긴다. crumb·쿠키·토큰·인증 URL·원문 예외 문자열을 저장하지 않는다. 응답에 담긴 API error와 빈 결과도 별도로 처리한다.
3. 프로필과 주가 조회를 독립시킨다. 프로필 실패가 주가 호출을 막으면 안 된다. 업종 미확인은 그대로 남기며 테마가 없다는 판단으로 바꾸지 않는다.
4. 설정에 요청 간격·동시성·최대 시도·실행 시간 한도를 둔다. 초기값: workers=2, 전체 요청 시작 간격 최소 0.5초, 총 3회까지, 재시도 대기 2초/8초+작은 jitter, 스크리너 시간 예산 25분. 기존 40분 워크플로 안에서 다른 단계 시간을 확보한다.
5. 429/5xx/timeout만 제한 재시도한다. Retry-After는 남은 예산 범위에서 적용한다. 401/403은 세션을 한 번 갱신해 확인한 뒤 반복 차단이면 해당 단계 중단·불완전으로 표시한다. 무한 재시도나 제한 회피용 프록시는 추가하지 않는다. 공유 opener/세션의 병렬 접근 방식을 명시하고 안전하게 관리한다.
6. 실패 목록에만 후속 재시도를 적용한다. 정상 수집한 수천 종목을 같은 실행에서 다시 읽지 않는다. 예산이 끝나면 미시도 목록과 수를 남긴다.
7. 단계별 요청/정상/자료부족/실패/미시도 수를 저장한다. 예: earnings 대상 3238 = 정상+자료부족+실패+미시도. 따로 quoted 누락 수도 기록한다. profile 대상은 후보 수, price 대상은 중복 제거 상위 후보 수다.
8. 운영 status는 기술적 실패·미시도가 하나라도 있으면 degraded, 핵심 입력 전체를 확보 못하면 failed, 정상 조사에서 후보가 없으면 정상적인 후보 0건으로 정의한다. unavailable은 실패로 세지 않되 커버리지로 표시한다. 실패율 경보 임계값은 status와 분리한다.
9. degraded여도 사용 가능한 결과는 저장한다. 문서 상단과 운영 보고서에 단계별 불완전 상태를 표시한다. 기존 결과를 최신 성공인 것처럼 보여주지 않는다. failed는 종료 코드 1; degraded는 코드 0이어도 명시적 상태 경고를 유지한다.

완료 테스트: 프로필 403이어도 주가 함수 호출, 429 후 성공, 지속 403 중단, 예산 초과 미시도, HTTP 200+API error, 분석가 미달 자료부족, 모든 프로필 실패 시 success 금지, 실패 목록만 재시도. 네트워크·시간·sleep은 주입/모킹해 오프라인 테스트한다.

## 5. 구현 작업 B — 비교 정의와 실행별 이력 (A 다음)

대상: 스크리너, persist_state, 관련 테스트와 결과 문서.

1. 요청 티커와 응답 티커를 검증할 식별 모듈/필드를 확보한다. EPS 통화 USD, 대상 기간 ISO 날짜, 숫자 finite, 현재 가격 양수, 분석가 수 유효성을 검증한다. 확인 불가 입력은 순위에서 제외하고 이유를 저장한다. 회계기준은 제공자가 명시한 경우만 확정하고 그 외 unknown으로 저장한다.
2. 0인 과거 EPS는 제공자 결측과 실제 0을 현 단계에서 구분하기 어려우므로 비교 제외로 유지하되, ‘신규 커버리지 확정’이라고 해석하지 않는다. 음수→양수는 성장률 대신 전환 표시를 우선한다. 반올림 전 원값으로 임계값을 판정한다.
3. 주가 비교는 동일 chart 응답의 두 정규장 종가와 거래일을 사용한다. 조정 기준을 확인·저장하고 서로 다른 기준은 섞지 않는다. 원시 종가 기준 PER 참고값과 조정 가격 수익률은 필드와 설명을 분리한다. 분할 등으로 EPS/주가 비교 기준을 맞출 수 없으면 PER은 미산출한다.
4. eps_target_period, eps_basis, eps_currency, provider_history=true, eps_retrieved_at, price_dates, price_basis, source_url, schema_version을 보존한다. 과거값의 대상 기간 일관성을 확인하지 못하면 그 한계를 표시하고 시장 미반영 근거로 승격하지 않는다.
5. 파일명을 `{UTC시각}_{run_id}.json.gz`로 바꾸고 실행마다 새 파일을 쓴다. root glob을 유지하면 기존 persist_state 규칙도 사용할 수 있다. 기존 날짜 파일은 삭제·재작성하지 않는다. 문서는 실제 파일을 링크한다.
6. 스냅샷에 적용한 설정, 코드 버전, 시작/종료 시각, 단계별 결과, 재현에 필요한 earnings 필드 전체와 원문 출처를 담는다. 세션 인증 정보는 제외한다. derived rows와 source payload를 분리한다.
7. latest 문서는 최신 시도 상태와 마지막 정상 결과 시각을 함께 보여준다. 실패 결과가 이전 정상 결과를 ‘오늘의 정상 결과’로 대체하면 안 된다. 원장에 제공자의 90일 전 값을 소급 입력하지 않는다.

완료 테스트: 통화/기간/티커 불일치, NaN/Infinity, 실제 0 비교 제외 이유, 반올림 경계, 가격 조정 불일치, 같은 날 두 실행 파일 보존, 이전 파일 읽기 호환, 저장된 payload+설정으로 점수 재계산 동일.

## 6. 구현 작업 C — 일간 실행 완료와 재시도 (독립 커밋)

대상: `.github/workflows/daily_discovery.yml`, 새 `scripts/daily_run_state.py`와 테스트, persist_state 허용 목록.

collect.checked_at 기반 생략을 제거한다. KST 업무일별로 daily_run_id, 단계별 상태, 시작·종료·마지막 성공·설정 버전을 기록한다. 필수 단계 집합을 코드/설정 한 곳에서 정의하고 문서화한다. collect, extract, tracked EPS, quarterly, screener, prices, views, returns 등 실제 일간 단계를 명시하며 요일별 단계는 해당 요일에만 요구한다.

- auto/예약: 오늘의 필수 단계가 완료됐으면 명령 처리만 한다. 미완료면 실패·미시도 단계와 그 의존 단계만 재개한다. 정상 조사 결과 0건과 실패를 구별한다.
- daily: 명시적 전체 재실행을 허용하되 새 run_id로 이력을 남긴다. 기존 알림 중복 방지를 유지한다.
- collect 실패 시 extract를 이전 latest 원문으로 실행하지 않는다. 가격·분기 수집 등 독립 단계는 계속한다.
- 단계 성공 기록은 산출물 저장 이후 쓴다. Git push 실패면 원격 완료 기록이 없으므로 다음 실행에서 복구/재시도가 가능해야 한다. 이전 성공 결과를 되돌리거나 force-push하지 않는다.
- 명령 처리 run은 일간 완료로 세지 않는다. 두 PC dispatch는 기존 writer concurrency 안에서 최신 원격 상태를 읽고 판단한다.

완료 테스트: collect 실패 후 auto 재개, collect 성공+screen 실패 후 screen 재개, 완전 성공 후 생략, 두 dispatch 직렬 실행 시 중복 억제, 자정 KST 경계, commands가 일간 완료로 오인되지 않음, push 실패 이후 재개. 대규모 워크플로 분해 전 작은 상태 판정 순수 함수로 테스트한다.

## 7. 구현 작업 D — 후보를 읽고 추적하는 흐름

A–C 검증 후 수행한다. 스크리너 상위 순서를 곧바로 추적 추천 순위로 바꾸지 않는다.

후보 카드는 회사 이름/티커, 한국어 한 줄 사업 설명, 이익 변화 수치와 대상 기간, A/B 선정 이유, 관측 시각/출처, 시장 미반영 판단의 근거·한계, 지속 근거, 반증 조건, 다음 확인 질문을 담는다. 값이 없으면 미확인으로 적으며 LLM이 숫자·출처·해소 조건을 만들어 채우지 않는다.

처음에는 후보 발견 / 자료 보강 필요 / 추적 추천 / 사용자 추적 중 / 종료를 구분한다. 기존 검토 상태·사업 단계·근거 수준 enum을 대체하지 말고 표시상 단계와 데이터 매핑을 먼저 설계한다. 새 테이블/컬럼이 필요하면 schema.json과 백업 마이그레이션을 같이 변경한다.

추적 추천은 원문 근거로 사업 이익 경로·지속성·반증을 설명할 수 있을 때만 제시한다. 숫자 스크린만 있으면 후보 발견이다. 미반영 판단은 PER 감소 하나로 확정하지 않는다. 사용자 선택 전 기존 watchlist나 investment_review_log를 자동 변경하지 않는다.

Telegram에는 `/screen` 조회와 하루 최대 3개 신규 후보 알림을 추가한다. 기존 정책의 하루 한도를 다른 후보 알림과 공유한다. 후보+가설+근거 개정으로 중복을 막고, 유지된 순위만으로 매일 새 후보처럼 발송하지 않는다. 명령 큐·메시지 길이·HTML escaping·재시도는 기존 안전 규칙을 사용한다. 실제 전송 검증은 사용자 승인 범위에서 한 번만 수행하고 영수증을 남긴다.

완료 테스트: 출처 없는 추천 차단, 자료 누락 표시, 사용자 선택 전 추적 원장 불변, 중복 후보/공유 일일 한도, 전송 실패 재시도, `/screen` 큐·응답, dry-run에서 상태/외부 메시지 변경 없음.

## 8. 후속 설계와 문서 정리

- 급등 사례의 주장마다 원문 URL·발표일·단위·기간·관측일을 저장소에 옮긴다. 당시 알 수 있었던 정보와 사후 해석을 분리한다. 확인하지 못한 숫자는 검증 대기로 표시한다. 성공 사례 외에 같은 신호가 났지만 성과가 없었던 비교 사례도 수집한다.
- 선행 신호는 가격 인상·공급 제약·수주잔고·전망 상향 폭 순서로 확장한다. 업종별 단위와 기간 정의를 먼저 정하고 같은 뉴스의 재배포를 독립 근거로 세지 않는다.
- 웹 화면은 후보 목록 → 후보 상세 → 사용자 추적 목록 → 관측 이력 순서. DB/상시 서버 이전은 지연 없는 명령 응답, 동시 쓰기, 다중 사용자 등 요구가 실제로 생길 때 별도 설계한다.
- CLAUDE.md의 오래된 4·6절 참조와 매매 행동 형식을 제거하고 AGENTS를 단일 기준으로 유지한다. STATUS의 과거 완료 기록은 보존하되 최신 미해결 항목을 맨 위에서 명확히 한다.

## 9. 구현 담당자에게 전달할 작업 방식

첫 구현 범위는 **A와 B**다. C는 다음 독립 변경, D는 수집 품질 확인 후 시작한다. UI·DB 이전까지 한 변경에 섞지 않는다. 막힌 부분은 임의 추정으로 완성하지 말고 입력·관측 증거·가능한 선택지를 남긴다.

작업 시작 시 STATUS, AGENTS, git status를 확인한다. 상대 작업자와 같은 체크아웃/원장에 동시에 쓰지 않는다. 기존 변경을 삭제하지 않는다. 정책과 스키마의 단일 원천을 유지한다.

각 단계 인수인계에는 변경 파일·이유, 테스트 명령/개수/결과, 아직 미검증인 항목, 운영 상태/커버리지 전후, 재현 가능한 증거 경로, 다음 단계가 필요하다. 테스트 통과와 운영 데이터 정상 확보는 따로 보고한다. 운영 테스트는 전체를 반복 호출하기 전에 소수 대표 종목으로 접근과 필드 검증부터 확인한다.

최종 완료 기준: 72개 기존 테스트 유지 + 위 실패 시나리오 추가 통과, 비밀정보 비노출, 한 번의 운영 실행에서 실제 커버리지와 상태 표시 일치, 원격 저장 확인. 외부 서비스 때문에 미확보 데이터가 남으면 복구 완료라고 보고하지 말고 정확히 degraded 상태와 남은 범위를 보고한다.
