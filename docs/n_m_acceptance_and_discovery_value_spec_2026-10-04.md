### Codex 확인 요청에 대한 결정

1. **`EFFECT_AFTER` 확장 수용.** `$12 million gain lifted net income`의 금액은 순이익 값이 아니다. 기존 결함과 같은 의미 관계를 검사하는 확장이다. gain 자체를 지표로 삼는 정상 문장과 진짜 순이익 수준값을 계속 허용하는 시험도 있다.
2. **`rendered_at` 추가 수용.** 관측 시각과 렌더 시각은 다른 개념이다. 현재처럼 관측 ID에 넣지 않고 기존 관측을 다시 쓰지 않는다. 동일 관측 시각에서는 생성기 번호, 렌더 시각 순으로 선택한다. 이 날짜를 최초 발견일이나 공시 발표일로 사용하지 않는다.
3. **성장률 지표의 level/delta 병행 허용 수용.** TEAM 2건은 매출 성장률 전망, MPC는 MPLX 배당 성장률 전망이므로 비율 자체의 값과 변화율이라는 표현이 양립한다. 매출 금액·순이익 수준값에 이 예외를 확대하지 않는다. TEAM 기간은 계속 미확인이고 MPC는 자회사 범위다. TXO도 figure 자체에 `decreased ... by`가 있는 고정 사례의 옛 메타데이터 호환만 허용한다. 일반적인 변화 금액을 level로 인정하는 근거가 아니다.

## 4. N1 — 발굴 경로의 분모와 누락 원인

평가 기준은 `b358704`에 보관된 2026-10-04까지의 자료다. 다음 일간에 입력이 늘어도 이번 기준 자료를 바꾸지 않는다. 최신 기준 스크린은 `data/processed/revision_screen/20261004T060125Z_37181539693-1.json.gz`다.

읽을 파일:

- `data/processed/revision_screen/*.json.gz`, `candidates/index.json`, `candidate_observations/`, `candidate_history/`
- `candidate_context_state.json`, `candidate_context_history/`, `company_documents/`, `data/eval/l4_2026-10-04/`
- `data/raw/discovery/`, `source_state.json`, `signal_log.csv`, `candidate_alerts.json`, `notify_state.json`, `daily_runs.json`
- `config/research_policy.json`, `config/discovery_sources.json`, `config/entities.json`(실제 식별 매핑 사용)

필수 집계:

1. EPS 경로: 조회 대상 → 비교 가능한 자료 → 조건 통과 → 카드 대상 → 원문 확보 → 초안 요청/응답 → 핵심 근거 확보 → 실제 알림. 단계가 서로 다른 집합이면 억지로 하나의 깔때기로 합치지 말고 각 분모를 적는다. 미확보·미시도·503·조건 미충족·상위 순위 밖·예산 대기·알림 중복 제한을 분리한다.
2. 사업 변화 경로: 수집된 공식 발표/뉴스 → 실제 후보 신호 → 원문 근거 → 알림. legacy/example/quarantine과 이미 추적 중인 기업의 갱신은 신규 발견에서 제외한다. 화면·발송 상태만으로 유망 여부를 정하지 않는다.
3. 날짜별과 고유 기업 기준을 둘 다 낸다. 시도 횟수, CTX 수, 기업 수를 혼용하지 않는다. `20261001T150156Z` 파일은 KST 10/2다. CIK/거래소·티커 확정 매핑이 없으면 이름 유사성으로 합치지 않고 `식별 미확인`으로 남긴다.
4. 알림은 실제 `sent` 영수증을 기준으로 한다. bootstrap·쿨다운·하루 한도 때문에 안 보낸 건과 조사하지 않은 건을 나눈다. 과거 알림 본문이 없으면 당시 사용자에게 보였을 문장을 추정하지 않는다.
5. 반복 등장, 업종 집중, 공식 발표일→최초 보관일→최초 후보일→최초 알림일을 기록한다. 날짜가 없으면 null이다. 120일 전 발표를 최근 다시 읽은 것은 신규 사업 변화와 구분한다.

이 단계는 원인 파악용 집계다. 세계 전체 유망 기업에 대한 재현율이나 투자 적중률을 계산하지 않는다. 원시 수집의 탈락 기록이 없어 분모를 복원할 수 없는 구간은 `측정 불가`로 명시한다.

### 사례별 작성 항목

각 사례는 아래 항목을 짧게 작성하고 모든 구체적 사실에 원문 위치나 저장 필드를 연결한다. 판정은 원문을 읽은 구현 담당자의 검토이며 자동 생성 점수로 대체하지 않는다.

1. **무엇으로 돈을 버는가 / 무엇이 달라졌는가.** 회사 전체·사업부·고객을 구분하고, 실제 실적·회사 전망·시장 추정치를 분리한다.
2. **회사 이익에 얼마나 중요한가.** 가격·물량·제품 구성·비용·세금·주식 수 등 이익으로 이어지는 경로와 규모를 제시한다. 비교 가능한 분모가 없으면 중요도 미확인으로 둔다. 서로 다른 기간·GAAP 기준·범위의 숫자를 나누어 비율을 만들지 않는다. EPS 증가분을 영업이익 증가분으로 바꾸지 않는다.
3. **지속될 근거와 일회성 요소.** 계약/계획/실현을 나누고 원문이 말하는 기간을 적는다. 매출 성장 하나로 구조적 병목이나 지속성을 확정하지 않는다.
4. **시장 기대와의 차이.** 확보한 같은 대상 기간의 추정치와 무엇을 비교할 수 있는지 적는다. Yahoo의 제공자 과거 값은 당시 직접 관측한 컨센서스가 아니며 과거 기간 일치도 확인되지 않았다. 주가가 덜 올랐거나 PER이 낮아졌다는 이유만으로 미반영을 확정하지 않는다. 원인 연결이 없으면 `미확인`이다.
5. **반대 근거와 틀렸다고 볼 조건.** 확인된 위험 사실과 앞으로 확인할 가설의 반증 조건을 구분한다. 별도 출처가 없으면 독립 교차확인 미실시다. 비GAAP 일반 면책만으로 실질 경고를 채우지 않는다.
6. **다음 점검.** 어떤 지표·발표에서 무엇을 확인하면 조사 지속/보류 판단이 달라지는지 한 가지를 적는다. 공시 일정이 미확인이면 임의 날짜를 만들지 않는다.
7. **두 가지 판정.** `원문 기준 조사 가치 = 우선 조사 / 보류 / 제외 / 판단 불가`, `현재 카드의 유용성 = 판단에 충분 / 중요한 근거 누락 / 오해 유발 / 카드 없음`을 별도로 적는다. 핵심 문제를 사례의 구체적 문장·누락 필드로 설명한다.

`우선 조사`는 이익으로 연결되는 구체적 변화와 조사할 이유가 있고 다음 검증 질문을 정할 수 있을 때다. 시장 미반영이 미확인이어도 조사 가치는 있을 수 있지만, 미반영이 입증됐다고 쓰지는 않는다. `제외`는 근거를 확인한 뒤 이번 목적에 맞지 않는 이유가 있을 때다. 자료를 확보하지 못한 경우에는 `판단 불가`이며 나쁜 후보 수에 넣지 않는다. **우선 조사 0개도 허용한다.**

### 조사 범위와 시점

- M 적용 후 카드의 유용성은 저장 원문·초안의 **v9/cards-v7 오프라인 표시**로 평가한다. 과거 실제 전달된 v7/v5 카드와 섞지 않는다. 없는 과거 표시를 현재 렌더로 복원해 당시 성과로 세지 않는다.
- 보관 원문을 우선 사용한다. 없거나 핵심 판단에 부족할 때만 사례당 최대 2개 공식 문서를 읽기 전용으로 보완한다. SEC 전체 재수집·새 Gemini 실험을 시작하지 않는다. 공개일이 기준 날짜 이후인 자료는 이번 판정에 사용하지 않는다.
- 지금 추가 확보한 문서는 조회 시각과 공식 발표일을 둘 다 남겨 `사후 보완`으로 표시한다. 당시 시스템이 이미 확보한 것으로 세지 않는다. 공시의 실제 텍스트가 저장본과 다르면 차이를 남기고 맞춰 쓰지 않는다.
- 조사는 위 7개 항목의 판단에 필요한 범위로 제한한다. 12개 전체에 대한 심층 기업 분석·장기 밸류에이션으로 확대하지 않는다.

## 6. N3 — 결과에서 다음 개발 1~2개 선택

평가 보고는 다음 네 가지를 먼저 답한다.

1. 지금 더 조사할 가치가 있는 후보는 어느 것인가? 최대 3개, 각각 핵심 변화·가장 큰 불확실성·다음 확인을 제시한다. 자동 추적 추천 승인이나 원장 등록과는 별개다.
2. 실제 카드가 판단을 돕는가? N2의 카드 대상 6개 중 충분/누락/오해의 개수와 사례를 제시한다. 검증기를 통과한 문장이 많다는 이유로 충분 판정을 하지 않는다.
3. 놓친 조사 기회가 있는가? 표본에서 원문상 조사 가치가 확인됐지만 순위·문턱·수집/예산·표시/알림 때문에 도달하지 못한 사례만 구체적으로 적는다. ALAB는 경계 분석일 뿐 신규 발견 성공/실패 분모에서 제외한다. 뉴스에서 이미 알린 기업은 스크린 카드가 없다는 이유로 놓친 것으로 세지 않는다.
4. 무엇을 먼저 바꾸면 좋은 후보가 더 일찍, 더 명확하게 보이는가? **최대 2개**를 선정하고 나머지는 보류한다. 각 제안에는 영향받는 사례, 원인, 수정할 파일/함수, 사용자가 보게 될 전후 차이, 비용/요청 증가, 정확도 위험, 완료 기준을 적는다.

가능한 원인은 수집 대상/검색어 부족, 상위 목록 제한, EPS와 사업 변화의 연결 부족, 일회성 구분 실패, 핵심 근거 미표시, 모델 실패/예산 등이다. 어느 원인이 우선인지는 평가 결과로 정한다. 원인을 확인하기 전에 점수식을 추가하거나 모델을 교체하지 않는다. 소수 사례에 맞춘 상수·티커 예외를 넣지 않는다.

이미 이익 상향이 크게 진행된 사례를 발견했다고 '남들보다 먼저'를 입증할 수는 없다. 이번 결과에는 **원문 정확도 / 추가 조사 가치 / 조기 발견 여부 / 이후 성과**를 분리한다. 뒤 두 항목의 비교 자료나 관측 기간이 없으면 미측정이다. 새 발굴 조건의 성과는 조건을 정한 이후 표본에서 평가한다.

## 7. 파일·검증·인수인계

이번 N 작업에서 만들 산출물:

- `data/eval/n_2026-10-04/manifest.json`: 기준 커밋, 기준 날짜, 실제 사용 입력 경로·해시, 고정 12사례와 선정 사유, 사후 보완 자료 구분
- `data/eval/n_2026-10-04/funnel.json`: 단계/날짜/채널별 건수, 고유 기업 수, 누락 사유와 분모 정의
- `data/eval/n_2026-10-04/case_reviews.json`: 위 7개 항목·판정·근거 위치·검토자를 가진 12사례. 모르는 값은 null과 사유로 보존
- `docs/n_discovery_value_evaluation_2026-10-04.md`: 집계, 12사례 비교표, 우선 조사 0~3개, 개선 제안 0~2개, 미측정 한계
- 실제 실행일의 N0 확인 문서, `docs/n_handoff_2026-10-04.md`, `STATUS.md` 맨 위 인수인계

집계에 코드가 필요하면 평가 폴더 안에 읽기 전용 `export_inputs.py` 하나를 두고 재현 명령을 기록한다. 운영 `scripts/`나 schema에 평가를 위한 상시 기능을 추가하지 않는다. 기존 검증·표시 함수를 사본에서 재사용하고 모델/SEC 호출 경로를 실행하지 않는다. 평가 파일 외 기존 원장·CTX·관측·발송 자료가 바뀌지 않았는지 확인한다. manifest는 실제 입력을 읽은 뒤 작성하며 정상 입력에 맞추려고 원본을 수정하지 않는다.

검증은 표본 12개 누락/중복 없음, 날짜·채널·기업 집계 일치, 근거 경로/문단 확인, 운영 파일 불변, 집계 재현으로 충분하다. 문서/집계 작업만 했다면 Python 전체 454개를 반복하거나 새 평가 프레임워크를 만들 필요가 없다. 별도 운영 코드를 고쳤다면 그 변경에 필요한 시험과 기존 CI를 수행한다.

완료 보고에는 N0 운영 확인 여부, 원문으로 판정 가능한/불가능한 사례 수, 우선 조사 후보, 실제 누락 사례, 다음 개발 최대 2개를 먼저 적는다. N1~N3을 마친 결과를 Codex가 검토한 뒤 해당 개선의 구현 지시를 확정한다. PSX JV, 머리글 기간 상속, respectively, 인과 note, DK 일반 위험 분류, 503 회로 차단, 로컬 모델은 그 평가에서 우선순위 근거가 나오기 전까지 보류한다.
