# V1 보완 결과 — 식별 누락 거절, 카드 문구, 상태 오류 재시도 (2026-10-12)

작성: Claude, 2026-10-12. 지시: [V1 검토](v1_acceptance_review_2026-10-11.md)(Codex)의 보완1·보완2·8번 점검. 실제 Telegram 발송·모델 호출 없이 가짜 업데이트·전송으로만 검증했다. V2/V3·예약 시각·워크플로는 바꾸지 않았다.

## 보완1 — 식별 정보 누락은 연결하지 않음

| 상황 | 이전 | 지금 |
|---|---|---|
| 답장 대상의 봇 표시(`from.is_bot`) 없음 | 연결(None 허용) | `unverified`: 기록 없음, ID 명령 안내 |
| 원 메시지 시각 없음 | 시각 검사 건너뛰고 연결 | `unverified` |
| 영수증 시각 없음·읽을 수 없음·시간대 없음 | 건너뛰거나 예외 가능 | `unverified`(예외 없음) |
| 봇이 아님 | `not_alert` | 그대로 |
| 원 메시지 시각이 영수증과 10분 밖 | `ambiguous` | 그대로 |
| 원 메시지는 맞고 사용자 답장은 며칠 뒤 | 연결 | 연결(비교 대상은 원 메시지 시각, 답장 시각 아님) |

- `candidate_feedback.resolve`는 운영 답장 전용으로 위 조건을 모두 요구한다. 공통 매칭은 `matches`/`linkable`로 나눴다.
- CLI `--dry-run --reply-to`는 새 `lookup_unverified`(봇·시각 검사 없음, 기록 없음)를 쓰고 출력에 `[dry-run·진단: 봇·시각 미검증 조회]`로 표시한다. 운영 `resolve`는 약화하지 않았다.
- README: 10분 대조는 같은 메시지 확인용 보조이며 '우리 봇' 보증이 아니라는 점, 채팅·봇 교체 시 기존 영수증에 자동 연결하지 않고 scope 변경·이전은 식별 확인 후 이관한다는 규칙을 적었다.
- 실제 원장 확인(읽기만): candidate_id 있는 발송 알림 21건 모두 영수증 시각을 읽을 수 있다. 엄격해진 조건 때문에 실제 알림 답장이 막히는 건은 없다.

## 보완2 — 카드 변경과 숫자 변경 구분

`자세히` 회신의 버전 줄을 '알림 당시와 같은 카드 버전입니다' / '알림 이후 카드 내용이 변경되었습니다'로 바꿨다. '숫자'라는 말은 쓰지 않는다. EPS 필드 비교 기능은 추가하지 않았다.

## 8번 점검 — 상태 오류가 영구 거절로 끝나던 경로

점검 결과 고칠 경로가 있었다. `promote.track_candidate`는 입력 거절을 모두 `Refused`(사유 코드)로 결과화하므로, `telegram_cmd.track_result`까지 올라오는 나머지 ValueError는 저장 단계·원장 상태 오류다. `add_entry.process`의 스키마·enum 검증 실패, 원장 셀 JSON 손상, `read_live_rows` 오류 등이다. 그런데 이전 코드는 이것을 `rejected / invalid_record`로 기록했다. 일반 `/track CAN-…`에서는 '식별·통화 확인 부족'이라는 틀린 회신으로 완료했다.

- `track_result`: Refused 이외의 ValueError(JSONDecodeError 포함)는 `promote.TrackStateError`(RuntimeError)로 바꿔 올린다. 명령 큐가 이것을 재시도 대상(`last_error_type`)으로 남긴다. 답장의 판단 이벤트는 이미 저장된 상태로 유지되고 track_result는 기록되지 않는다. 재처리 때 `tracked_before`로 성공이 그대로 성공으로 남는다.
- `invalid_record`는 저장 전에 판정되는 영구 입력 오류로 좁혔다. 지금은 후보 카드의 관측 시각(`observed_at`)을 읽을 수 없는 경우 하나뿐이다(promote가 `Refused("invalid_record")`로 거절). 회신은 '관측 시각이 올바르지 않아 등록하지 않았습니다'이며, `observation_in_future`에도 같은 문구를 쓴다. 이전에는 식별·통화 부족 문구였다.
- `/track SIG-…`·티커 경로(`promote_signal`)와 큐의 일반 ValueError 처리는 이번 범위가 아니라 그대로 두었다.
