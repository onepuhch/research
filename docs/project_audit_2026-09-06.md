**4. 투자 방향성과 분석 내용에서 고쳐야 할 점**

**① “시장이 모르는 소형주”를 “시장 기대보다 이익 귀속이 큰 기업”으로 바꾼다.**

작은 시가총액, 낮은 주가 상승률, 낮은 인지도는 미반영의 증거가 아니다. 순수 플레이어도 고객의 협상력이 강하거나 경쟁 증설·희석이 크면 주주에게 이익이 남지 않을 수 있다. 반대로 이미 알려진 기업도 이익 규모나 지속 기간을 시장이 잘못 추정할 수 있다.

현재 `collect.py:230`은 메가캡 공시를 본문 수집 전 제외한다. 이는 투자 후보 필터가 정보 수집까지 제한하는 구조다. **대형 고객사는 수요의 근거로 적극 수집하고, 투자 후보 선정은 별도로 평가**해야 한다. 고객의 CAPEX·구매 계약·제품 로드맵이 중소 공급사의 병목을 찾는 핵심 단서가 될 수 있다. 회사 목록을 알고 추적하는 것도 허용하되, 새 신호를 기존 가설에 억지로 맞추지 않도록 찬반 근거를 함께 기록한다.

**② 병목의 존재와 주주의 수혜를 구분한다.**

각 가설에는 다음 인과관계가 필요하다.

`수요 변화 → 특정 공급 제약 → 가격·물량·믹스 변화 → 특정 기업의 매출·마진 → EPS·현금흐름 → 시장 기대와의 차이`

특히 CAPEX 발표는 신규 공급이 늘어 병목이 완화될 가능성과 자금 부담도 동시에 뜻한다. 공급업체 수가 적다는 사실만으로 가격결정력이 입증되지는 않는다. 다음을 조사해야 한다.

| 질문 | 필요한 근거 |
| --- | --- |
| 누가 병목으로 돈을 버는가? | 고객·공급사 관계, 해당 사업 매출 비중, 계약상 가격 전가 |
| 얼마를 벌 수 있는가? | 생산량·ASP·믹스·증분 영업이익률의 범위 추정 |
| 언제 실제 이익이 되는가? | 인증, 양산, 설비 가동, 매출 인식 일정 |
| 언제 병목이 풀리는가? | 경쟁 CAPA, 대체 기술, 고객 내재화, 재고 정상화 |
| 주주에게 얼마나 남는가? | 유지·성장 CAPEX, 운전자본, 순부채, 주식보상·증자 |
| 시장과 무엇이 다른가? | 날짜·기간·출처가 맞는 컨센서스와 자체 가정의 차이 |

**③ EPS 성장과 EPS 리비전을 분리한다.**

현재 CRDO 아이디어는 미래 분기 EPS의 상승 경로와 매출 성장률을 상향 모멘텀의 근거로 사용하지만, 같은 대상 회계연도의 추정치가 과거 관측 시점보다 얼마나 올라갔는지는 기록되어 있지 않다. `Q1 전망 → Q4 전망`은 서로 다른 실적 기간의 비교다. `6월에 본 FY2027 추정치 → 9월에 본 FY2027 추정치`가 리비전이다.

CRDO의 현재 투자 매력이나 당시 숫자의 정확성을 이 감사에서 재평가한 것은 아니다. 기록된 “중기” 판정을 프로젝트의 숫자 기준으로 재현할 근거가 부족하다는 진단이다. 최초 실전 추적 대상으로 기존 CRDO 가설을 다시 검증하면 연결 구조를 가장 빠르게 점검할 수 있다.

**④ “EPS 상향률 > 주가 상승률”을 저평가 판정으로 사용하지 않는다.**

동일 회계기간, 동일 EPS 정의, 양의 EPS, 동일 관측 구간이라는 조건에서 이 관계는 forward PER이 낮아졌음을 뜻한다.

`새 PER / 기존 PER = (1 + 주가 변화율) / (1 + EPS 추정치 변화율)`

예를 들어 EPS 추정치 +20%, 주가 +10%이면 PER은 약 8.3% 낮아진다. 그러나 기존 PER이 과도했거나 이익 지속성이 약해졌다면 여전히 비쌀 수 있다. 적자·0에 가까운 EPS에는 같은 해석을 적용하지 않는다. PER은 성장률뿐 아니라 위험과 이익 배분 구조에도 영향을 받는다. [Damodaran의 PE 설명](https://pages.stern.nyu.edu/~adamodar/New_Home_Page/invfables/peratio.htm)

따라서 이 수치는 “멀티플 변화 관찰 지표”로 유지하고, 정상화 이익·현금흐름·자본 부담·상승/하락 시나리오와 함께 평가한다. 가치 평가에 사용하는 가격은 EPS와 주식분할 기준을 맞추고, 성과 복기의 수익률은 배당·분할을 반영해 별도로 계산한다.

**⑤ 사업 단계·근거 수준·검토 상태를 분리한다.**

현재 단계표에는 사업의 진행, EPS 데이터 확보, 가격 반영 정도, 매매 행동이 한꺼번에 들어 있다. “EPS 상향 중단”은 중기 진입 요건 미충족과 종료 사유로 동시에 작동할 여지가 있고, 소액·증액·축소 지시는 리서치와 비중을 분리한다는 원칙과 충돌한다.

권장 구분은 다음과 같다. 사업 단계는 초기·확산·성숙·둔화, 근거 수준은 가설·단일 확인·독립 교차확인·시계열 검증, 검토 상태는 미검토·추적·재검토·종료로 둔다. 데이터 부족은 별도로 표시한다. 기존 단계명은 호환용 표시로 남길 수 있지만 가격과 자료 부족만으로 사업 단계를 바꾸지 않는다.

단일 기사에서 시작한 자동 결과는 가설 또는 단일 확인까지만 허용하고, 독립 지표와 시계열이 있어야 상위 근거 수준으로 이동시킨다. 필요한 기간이 쌓이지 않았다면 “미확인”으로 둔다. 긍정적 기사 여러 개를 같은 사실의 독립 확인으로 세면 안 된다.

**⑥ 초기 운영 범위를 병목 확산형·사이클 리비전형에 집중한다.**

현재 5개 아이디어 유형을 모두 허용하지만, 실질적인 판정 기준은 EPS 리비전 중심이다. 이벤트형·적자 턴어라운드형·가치 재평가형까지 같은 기준으로 판정하면 일관성이 깨진다. 첫 30일에는 프로젝트 철학과 가장 맞는 두 유형을 핵심으로 두고, 다른 유형은 별도 검토함에 보관한다. 유형별 기준이 마련된 뒤 넓힌다.

| P2 | 축별 점수의 근거와 모델 버전이 남지 않음 | 점수 재현·오류 분석 불가. 원문 인용·문서 위치·버전·판정 이유 저장 |
| P2 | raw 수집 자료는 gitignore이고 Actions에 보존 단계가 없음 | 실행 당시 발췌와 모델 응답을 재검토하기 어려움. 보존 정책을 정한 근거 저장소 또는 artifact에 연결 |
| P2 | 주간 보고가 현재 목록을 나열 | 강화·약화·미점검 항목을 알기 어려움. 직전 판단과 변화 비교로 전환 |
| P2 | CSV 전체 덮어쓰기, 원장과 처리 상태의 별도 저장 | 중간 실패 때 불일치·재처리 중복 가능. 임시 파일 교체·안정적 ID·복구 점검 우선 |
| P2 | 일부 컬럼·enum을 위치로 해석 | schema 순서 변경에 취약. notify의 review/sector와 telegram 경로까지 이름 기반으로 통일 |

**오탐은 추정만이 아니라 데이터와 재현으로 확인했다.** 원격 `SIG-0862`의 대출 관련 prepayments, `SIG-0865`의 모기지 증권 관련 문구가 수주/백로그로 분류되어 있다. 합성 대출 문장도 동일 분류를 재현했다. 590건은 요약 형식에 따른 키워드 경로 추정치이며 모든 행의 실제 API 실행 경로를 확인한 수치는 아니다. 이 가운데 B티어 3건도 존재한다. 다만 이를 전체 알림의 오탐률로 확대 해석해서는 안 된다.

사전 필터도 현재는 검색 문구 수와 본문 길이에 주로 의존한다. “투자를 계획한다”, “옵션을 확보했다”, “확정 계약을 체결했다”, “매출로 인식했다”를 다른 사건으로 추출해야 한다. 원격 A티어의 일부 계획 발표는 계획 단계 자체만으로 이익·수요가 확인된 듯한 해석을 받는다. 해당 기업의 투자 가치를 부정하는 것이 아니라 증거 단계가 섞이는 문제다.

**EPS 개선은 ‘유지 행 삭제’만으로 끝내면 안 된다.** 유지 관측을 모두 없애면 “확인했지만 변화 없음”과 “데이터 수집 실패”를 구별하지 못한다. 관측 스냅샷은 유지하고, 별도 뷰에서 유효 변경 이벤트·월별 순변화·마지막 상향일·데이터 신선도를 계산하는 것이 낫다. 90일 리비전은 실제 90일 전 baseline이 있어야 계산하며, 과거 자료가 없으면 기록 시작 이후만 표시한다.

추적 목록은 가능하면 활성 아이디어와 관측할 지표에서 생성해 이중 관리를 줄인다. 현재 설정 파일에 자동 추가하는 방식을 택하면 Actions의 저장 대상에도 해당 설정을 포함해야 한다. EPS 수집·기존 알림 재시도·명령 처리는 한 기능의 장애 때문에 나머지가 모두 생략되지 않도록 성공 조건을 구분한다.

**6. 외부 서비스와 운영 신뢰성**

Telegram은 미수신 업데이트를 24시간 넘게 보관하지 않는다고 명시한다. 하루 1회 polling과 지연 가능한 Actions를 결합하면, 즉시 응답이 필요 없더라도 명령 보존을 보장할 수 없다. 명령 처리만 별도 주기로 실행하고, 처리 실패 건은 내구성 있는 대기열에 저장한 뒤 확인 처리해야 한다. 현재의 `finally: save_offset(...)`는 내부 처리가 실패해도 해당 명령을 넘길 수 있다. [Telegram Bot API](https://core.telegram.org/bots/api)

수집은 하루 1회로 유지해도 된다. 정각을 피한 예약 시간은 검토할 수 있지만, GitHub는 예약 지연과 혼잡 시 누락 가능성을 문서화하므로 정시 실행을 전제로 설계하면 안 된다. “실행 안 됨”, “소스 실패”, “정상 수집·유효 신호 0건”을 구분하고 마지막 성공 시각과 자료 기준일을 표시한다. [GitHub 운영 문서](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows)

Gemini는 분당 요청·입력 토큰·일일 요청 등 여러 한도를 사용한다. 현재 `sleep(4)`만으로 일일 할당량을 해결할 수 없다. `STATUS.md`의 “하루 한 번이라 quota 무관”은 수정해야 한다. 실제 한도와 예산에 따라 하루 처리 건수를 조절하고 일시 실패는 다음 회차로 넘긴다. [Gemini rate limits](https://ai.google.dev/gemini-api/docs/rate-limits)

FMP는 코드가 구형 v3 endpoint를 사용한다. 이번 점검에서는 실제 키·플랜의 접근 권한이나 현재 응답 계약을 확인하지 않았으므로 “무료로 정상 수집 가능” 또는 “API가 고장났다”고 단정하지 않는다. 먼저 1종목의 실응답으로 회계기간·EPS 정의·가용 범위·현재 권한을 검증해야 한다. 공급자의 공식 v3 예시도 대상 실적 날짜별 추정치 배열을 보여주며 관측 시점별 리비전 이력과는 구분해야 한다. [FMP 공식 예시](https://github.com/FinancialModelingPrep/API3-integration)

SEC는 공시 이력과 XBRL 실적 API를 제공한다. 고객사·공급사의 실제 실적 확인에는 활용할 수 있으나 이를 애널리스트 컨센서스의 대체로 취급하지 않는다. 탐색용 키워드 검색과 기업별 공시 추적을 병행하고, 원문의 정확한 문서 URL과 인용 위치를 보존한다. 현재는 약 2,000자 발췌와 공시 폴더 URL만 남아 맥락 재검토가 불편하다. [SEC API 설명](https://www.sec.gov/search-filings/edgar-application-programming-interfaces)

**7. 권장 프로세스: 연구 질문부터 복기까지 연결한다**

`연구 질문 → 수요·공급 근거 수집 → 사실 검증 → 병목 가설 → 기업별 이익 귀속 → 시장 기대 비교 → 추적 등록 → 변화·반증 점검 → 복기`

| 단계 | 필수 산출물 | 다음 단계로 넘어가는 조건 |
| --- | --- | --- |
| 연구 질문 | 어떤 공급 제약이 어디로 옮겨가는지 한 문장 | 관측할 수 있는 지표와 출처 정의 |
| 사실 추출 | 주체·사건·수치·단위·기준 기간·원문 인용 | 문서의 실제 표현과 일치 |
| 병목 가설 | 수요와 공급의 불균형, 경쟁·대체 가능성 | 독립 근거 2개 이상을 초기 운영 기준으로 적용 |
| 기업 연결 | 특정 기업의 매출 노출·가격결정력·원가 부담 | 테마 연관성을 넘는 경제적 연결 근거 |
| 기대 차이 | 시장 추정과 자체 가정의 차이·확인할 사건 | 출처와 비교 기준이 일치하거나 미확인을 명시 |
| 추적 등록 | 기준 수치, 반증 조건, 다음 점검일 | 등록 후 실제 관측이 가능한 상태 |
| 주간 검토 | 지난 판단 대비 강화/유지/약화/자료 부족 | 변화를 만든 신규 근거 연결 |
| 복기 | 예상 사건과 실제 결과, 실패 원인 | 최초 판단을 덮어쓰지 않고 기록 보존 |

독립 근거 2개는 초기 운영을 위한 제안값이며 보편적 투자 법칙이 아니다. 같은 보도자료를 인용한 기사 5개는 근거 1개다. 가설 단계는 1개 신호로 열 수 있지만 검증 완료와 구별한다.

첫 운영 범위는 연구할 병목 2~3개, 활성 아이디어 5~10개 이하를 제안한다. 기존 AI 인프라 지도를 활용하되 어디를 우선할지는 최신 근거의 가용성과 실제 추적 가능성으로 정한다. 기업 수를 먼저 채우지 않는다. 시간이 부족하면 활성 수를 더 줄인다.

일일 보고에는 신규 검토 상위 3건, 기존 가설의 중요한 강화·약화, 데이터 이상을 담는다. 신규 후보가 없으면 없다고 보고하고 숫자를 채우지 않는다. 반증·종료 조건 관련 알림은 신규 후보 3건 제한과 별도로 다룬다. 카드에는 신호 ID, 발행일, 바뀐 사실, 가설에 미치는 영향, 반대 근거, 다음 확인 항목을 넣는다.

주간에는 60~90분을 초기 운영 가정으로 잡아 활성 아이디어의 기준 수치와 가설을 갱신한다. 새 종목을 찾는 시간과 기존 종목을 반증하는 시간을 둘 다 확보한다. 실적 발표 등 중요한 사건이 있으면 주간 일정을 기다리지 않고 검토한다.

**8. 필요한 최소 데이터 구조**

지금의 테이블은 활용하되 관계와 관측 기준을 보강한다. 아래는 설계 제안이며 이번 감사에서 schema를 변경하지 않았다.

| 영역 | 최소 추가 정보 |
| --- | --- |
| 기업 식별 | `entity_id`, 티커, 거래소, CIK, 별칭, 식별 유효기간 |
| 근거/신호 | `source_id`, 문서 URL, 발행·수집·처리 시각, 원문 인용, 모델·프롬프트 버전, 채택/거절/실패 이유 |
| 경제적 사건 | 사건 주체·객체, 계획/확정/실행 구분, 방향, 수치·단위·기간, 같은 사건의 중복 연결 |
| 병목 가설 | `bottleneck_id`, 밸류체인 노드, 수요·공급 근거 ID, 경쟁 증설, 예상 해소 시점 |
| 아이디어 | `idea_id`, 기업 ID, 가설 ID, 연결 신호 ID, 초기 가정, 다음 검토일 |
| 지표 | `as_of`, `period_end`, 회계연도·분기, provider, 통화·단위, GAAP/조정 기준, 값, 기준 표본 수 |
| 판단 이력 | 변경 전후 상태, 변경 이유, 근거 ID, 변경 시점, 평가 기준 버전 |
| 실행 상태 | 소스별 수집 성공, 거절·대기·재시도 수, EPS 관측 수, 마지막 성공 시각 |

동일 종목이라고 모든 아이디어를 하나로 합치면 안 된다. 같은 기업의 다른 가설은 별도 아이디어가 될 수 있다. 반대로 같은 가설의 뉴스가 여러 번 나왔다는 이유로 새 아이디어를 계속 만들면 안 된다. 권장 중복 키는 기업·가설과 원신호 ID를 함께 고려한다.

현 단계에서는 CSV를 유지하고 원자적 파일 교체·ID 연결·변경 이력부터 보강하는 편이 변경 위험이 작다. 동시 쓰기, 복잡한 관계 조회, 원장과 처리 상태의 거래 단위 저장 필요가 실제로 커지면 SQLite를 원장으로 사용하고 CSV는 내보내기로 전환한다. Actions의 매번 새 실행 환경에서 DB를 어디에 영속화할지도 함께 정해야 하므로 파일 형식 변경만으로 문제가 해결되지는 않는다.

**9. 점수와 성과 측정 개선**

`upside_score`는 검증되지 않은 투자 기대수익으로 읽히기 쉽다. 설계 문서의 A=10배, B=3~5배 의미를 제거하고 **A=우선 검토, B=추가 확인, 관망=근거 부족**처럼 연구 우선순위로 정의하는 편이 낫다. 근거가 없는 점수는 미확인으로 남기며, 작은 시가총액이나 AI라는 단어만으로 가점을 주지 않는다.

단일 합계보다 세 요소를 구분해 보인다: 증거의 질, 기업의 경제적 노출, 시장 기대와의 차이. 소형 기업에는 현금 소진·조달·희석·고객 집중을 별도로 점검한다. 부족한 근거를 다른 축의 높은 점수로 상쇄해 A로 만드는 구조를 피한다.

| 측정 항목 | 정의와 주의점 |
| --- | --- |
| 사실 추출 정확도 | 원문 대비 기업·사건·수치·단위·기간 일치율 |
| 검토 가치 비율 | 상위 후보 중 사람이 추가 연구할 가치가 있다고 판단한 비율 |
| 추적 완료율 | 활성 가설 중 기준 지표·반증 조건·다음 점검일이 갖춰진 비율 |
| 갱신 준수율 | 기한 내 검토한 활성 가설 / 검토 예정 가설 |
| 발견 선행성 | 최초 유효 신호부터 사전에 정한 확인 사건까지 걸린 기간 |
| 예측 적중 | 미리 정한 기간·조건의 사건이 실제 발생했는지 |
| 투자 성과 | 당시 확정된 평가 규칙과 벤치마크 대비 총수익률·낙폭 |
| 운영 효율 | 검증된 가설 1건당 사용 시간·호출 수·비용 |

수익률 평가는 업종·시장 전체 상승과 구분해야 한다. 수익률을 잘 맞힌 경우에도 근거가 맞았는지 별도로 평가한다. 보유 기간을 고정하지 않는 투자 철학과 30/90/180일의 표준 복기 기간은 양립한다. 후자는 비교를 위한 측정 창이다.

과거 승자만 해부하면 선택 편향이 생긴다. 전체 검토 후보, 거절·관망, 실패 기업을 포함하고 당시 알 수 있었던 자료만 사용한다. 처음에는 A/B/관망을 나눠 50~100건을 수작업 판정하되, 동일 기업·사건의 중복을 통제한다. 과거 표본에서 조정한 기준은 뒤 시기의 별도 표본으로 확인한다. 첫 달에는 과거 데이터를 이용한 파이프라인 검증과 앞으로 쌓는 실전 관측을 구분하며, 월별 연속성이나 알파가 검증됐다고 주장하지 않는다.

아래 순서는 현재 확인한 결함을 기준으로 한 제안이다. 개발 작업량이 아니라 완료 조건을 기준으로 다음 단계에 진입한다.

비용을 쓰게 된다면 우선은 현재 누락되는 핵심 데이터의 정의·신선도·회계기간 일치 문제를 해결하는 데 배분한다. 이후 고난도 원문 해석에만 더 강한 모델을 제한적으로 사용한다. 공급자의 이름이나 모델 성능만으로 데이터 품질과 투자 성과가 보장되지는 않는다.

**12. 검증 결과와 분석의 한계**

Python 파일 13개의 구문을 확인하고 원격·로컬 동일성을 검증했다. 네트워크 호출을 대체하거나 임시 원장을 사용해 다음 8개 동작을 확인했다.

1. 대출 조기상환 문장이 수주/백로그로 분류됨.
2. 상향→상향→유지의 연속 상향 수가 0으로 계산됨.
3. 거절 항목이 두 번 실행에서 두 번 재처리되고 seen에 남지 않음.
4. 단일 기사에 대해 모델이 반환한 “중기”가 통과됨.
5. 같은 신호를 두 번 승격하면 아이디어 2개가 생성되고 원신호 ID가 보존되지 않음.
6. FY2027·FY2028 추정치를 주면 FY2028 한 개가 선택됨.
7. 과거 날짜·다른 공급자 행을 마지막에 입력하면 그 값이 이전 지표로 선택됨.
8. 전날 신호는 `/track 티커`로 찾지 못하지만 신호 ID로는 찾을 수 있음.

또한 지표 발굴 보드는 6월 3일 예시 2건을 9월 6일에도 “연속 상향 2회” 후보로 출력했다. 이것은 코드 동작 점검이며 과거 시장 상황의 재현이나 투자 수익률 백테스트는 아니다.

이 분석이 틀릴 수 있는 부분은 저장소 밖에서 수행되는 수동 연구를 보지 못했다는 점이다. 별도 문서에서 활발히 점검했다면 “연구가 없다”는 결론은 성립하지 않는다. 다만 그 경우에도 자동 시스템이 그 판단을 기록·추적하지 못한다는 연결 문제는 남는다. 전체 865건을 원문과 전수 대조하지 않았으므로 전체 오탐률은 미측정이다. 무료 API의 현재 권한·실제 응답과 Sheets 배포 상태 역시 별도 검증이 필요하다.
