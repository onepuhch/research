## 3. 구현 순서와 필수 보완

각 F를 별도 커밋으로 구현한다. 순서 **F1 → F2 → F3 → F4 → F5 → F6**. 관련 질문의 작은 UI/검증 변경은 해당 F에 묶는다. 모든 F가 끝나기 전 추가 자동 알림 기능이나 DB 이전을 시작하지 않는다.

### F1. 내용 버전과 실제 관측 이력

대상: candidates.py, promote.py, schema.json, persist_state.py, 후보 관련 테스트.

확인한 문제:

- store_versions는 같은 버전이면 기록하지 않는다. known_candidates는 그 파일의 최초 observed_at만 모은다. 9/25와 10/10에 같은 내용을 관측한 모의 입력에서 마지막 시각이 9/25로 남았다. 다음 날 목록에서 빠지면 find가 최초 관측을 반환하므로 14일 신선도 판단이 틀릴 수 있다.
- 내용 A→B→A로 돌아오면 파일 생성시각으로 정렬한 B를 마지막 내용으로 오인할 수도 있다.
- 현재 eps 안의 yield_change_*는 가격을 분모로 쓰는 값이다. 주가 구간만 해시에서 빼도 '가격 때문에 내용 버전이 바뀌지 않는다'는 설명은 성립하지 않는다.

구현:

1. candidate_version은 EPS 원수치·기간/기준·식별·사업 설명·근거·자료 상태·A/B 편입 분류처럼 카드의 주장을 식별한다. 날짜/순위/가격 구간과 yield_change 수치는 observation으로 이동한다. A/B 편입 자체가 바뀌면 버전 변경은 허용한다. 기존 CV 파일을 수정하지 말고 generator/schema 버전을 올린다.
2. `candidate_observations/{observation_id}.json`을 불변 저장한다. ID는 후보 ID+원자료 SHA256+내용 버전+정책 버전의 해시로 생성한다. candidate_id/version, 실제 observed_at, source_snapshot 경로·전체 SHA256, EPS 표시값, 주가 원값/실제 날짜/수익률/PER 참고값, 순위/편입/quality, 정책 버전을 포함한다. 동일 입력 재렌더는 같은 ID로 중복 저장하지 않는다.
3. index/known은 이 관측에서 재생성한다. first_seen/last_seen과 최신 observation/version을 분리한다. A→B→A를 시간순으로 정확히 복원한다. 이전 CV만 있는 자료는 최초 기록만 이관한다. 기존 원자료에서 검증 가능하게 재구성할 때만 과거 관측을 추가하고 재구성 여부/시각을 남긴다. 없는 날짜는 만들지 않는다.
4. /candidate, /track, 알림 이벤트가 observation_id를 참조하게 한다. 과거 카드에도 당시 주가·날짜·미확인 사항을 보여 준다. 등록 당시 스냅샷은 이 참조로 고정한다. 과거 승인/영수증 참조는 마이그레이션 후에도 해석 가능해야 한다.
5. 신규 등록 신선도는 실제 마지막 관측의 KST 날짜로 판정하고 미래 관측은 거부한다. 이미 연결된 활성 동일 가설은 신선도 검사 전에 기존 ID를 반환한다. 종료된 가설을 자동 재개하지 않는다.
6. verified_target은 관측시간/등록 참조로 결정한다. CV 해시 이름의 사전순을 시간으로 사용하지 않는다.

필수 테스트: 동일 버전 16일 재관측 후 목록 이탈, A→B→A, 주가만 변화(분류 동일), FY 변경, 당시 등록/발송 화면 재현, 미래 날짜 거부, 오래된 반복 /track의 무쓰기 멱등성, 역순 해시와 실제 시간 불일치, 기존 이력 불변, persist allowlist 포함.

### F2. 명령 처리와 일간 계획 순서

대상: daily_discovery.yml, daily_run_state.py, telegram_cmd.py, 워크플로 통합 테스트.

현재 YAML은 plan(52행) → commands(57행) 순서다. 오늘 일간 완료 뒤 같은 auto에서 /track을 처리하면 RUN_EPS 등은 이미 false여서 새 종목 수집이 다음 auto로 밀린다. 함수의 tracking_revision 테스트만으로 이 순서를 검증할 수 없다.

- recover/migrate → commands → plan → 일간 단계 순으로 옮긴다. 명령 실패가 독립적인 일간 계획까지 막지 않도록 조건을 명시한다. plan은 마이그레이션 성공을 전제로 한다.
- auto에서는 새 추적 대상 때문에 eps/quarterly/prices/cards/views가 같은 실행에서 계획돼야 한다. commands 모드는 명령만 처리하고 다음 auto에서 수집한다. 답변은 '다음 auto 일간 실행에서 수집, 자료 확보 여부는 /data로 확인'처럼 모드에 맞는 사실을 말한다.
- baseline이 활성 아이디어/신호를 읽는 실제 입력도 그래프에 반영한다. 신규 등록 같은 날 baseline→returns→views가 빠지지 않도록 입력을 확인한다.
- finish는 필수 단계 미완료를 실패로 보고하되 persist_state/upload는 always로 보존한다. 실행 완료와 품질 완전성을 별도 출력한다.

필수 테스트: 오늘 전 단계 완료→명령 큐 신규 CAN 등록→동일 auto에서 수집 대상 포함, 동일 명령 반복→불필요 재수집 없음, commands→수집 0, 명령 응답 실패와 일간 실행 독립, blocked만 남은 실행의 최종 실패.

### F3. 뉴스 후보 누락과 채널 중복

대상: notify.py, candidate_alerts.py, research_policy.json, 알림 테스트.

재현: news_items는 notify.select_signals를 쓰고 이 함수는 중복 이벤트 검사 전에 상위 3개로 자른다. 그 3개가 기존 발송과 같은 기업·가설이고 signal_id만 새 것이면 select에서 모두 버린다. 4번째 신규 기업은 보지도 못한다. 모의 뉴스 4개에서 pool=3, 최종 선택=0을 확인했다.

- 뉴스 적격 필터/정렬을 일일 발송 제한과 분리한다. 모든 적격 뉴스에서 식별 정규화→이벤트 중복/기업 간격/신선도 검사→뉴스·스크린 교차 배분→최대 3개를 적용한다. 기존 위험 알림 경로는 유지한다.
- 공용 policy `candidate_alerts.entity_new_cooldown_days=14`. KST 날짜 차이가 14 미만이면 신규 발견 억제, 14 이상이면 다른 가설/채널의 신규 이벤트 허용. 같은 이벤트는 기간이 지나도 재전송하지 않는다. bootstrap 기업은 이미 본 목록이며 실발송 시각을 날조하지 않는다.
- sent/reserved/uncertain은 중복 억제에 포함한다. 과거 notify_state의 signal_id는 signal_log와 연결해 기업을 찾고 일일 기업 중복·14일 간격에 반영한다. 못 찾으면 unknown으로 남긴다.
- CIK와 거래소:티커가 같은 기업이면 기존 registry의 확정 매핑으로 통일한다. 종목명 유사성만으로 합치지 않는다. 표시 문구도 '기업을 영구히 다시 알리지 않음'이 아니라 실제 규칙을 설명한다.

필수 테스트: 상위 3개 기존 이벤트+4번째 신규, 같은 기업 다른 가설 13일/14일 경계, 뉴스→스크린/스크린→뉴스 대칭, 승인 이벤트 예외와 당일 기업 1회, legacy 발송, 초기 29개 재알림 없음, 위험/명령 응답 비차감.

### F4. 전송 결과와 CI 중단 복구

대상: notify.deliver, candidate_alerts.py, persist_state.py 또는 후보 outbox 전용 모듈, workflow, 관련 테스트.

재현: `{"ok":true,"result":{}}`에 현재 deliver는 `sent, message_id=None`을 반환한다. 그리고 reserved의 atomic_json은 러너 로컬 파일에만 저장된다. 전송 뒤 최종 persist 전에 러너가 종료되거나 push가 거절되면 다음 checkout에는 예약도 영수증도 없어 재전송할 수 있다. 파일 원자적 쓰기와 원격 보존은 다르다.

1. sent는 올바른 dict 응답, ok=true, result=dict, 유효한 정수 message_id가 모두 있을 때만 인정한다. 누락/타입 오류/읽기 중단은 uncertain. URLError라는 이유만으로 '연결 전 실패'라고 단정하지 않는다. DNS/연결 거부 등 확실한 미전송만 failed, 요청 송신 여부가 불명확한 연결 끊김은 uncertain으로 둔다. HTTPException도 처리하고 비밀 포함 예외 문자열은 기록하지 않는다.
2. 후보 전송을 prepare/reserve → 원격 보존 성공 → dispatch → 영수증 보존으로 나눈다. payload 해시, observation 참조, event key, 예약일, 실행 ID/시도 ID를 저장한다. 원격 예약 push 실패 시 네트워크 전송 0회다. 기존 research-state-writer 안에서 운영 상태 allowlist를 재사용하며 임의 파일을 stage하지 않는다.
3. 예약을 만든 현재 실행만 저장한 예약을 발송할 수 있다. 다음 실행에서 발견한 옛 reserved는 uncertain으로 격리하고 자동 재발송하지 않는다. 전송 전에 중단돼 실제로 못 보낸 경우도 자동 재발송보다 누락을 택하며 운영 상태에 드러낸다. 영수증 push 실패 후에도 원격 reserved가 남아 중복을 막아야 한다.
4. 다음 날 uncertain/reserved가 있었다는 이유로 다시 신규 이벤트를 만들지 않는다. 확인된 failed는 같은 event key로 재시도하고 시도 이력을 유지한다. 길이 초과 뉴스는 출처/핵심 설명/추적 명령을 보존하는 명시적 요약을 만든다.
5. 이 변경은 후보 알림의 복구 범위를 우선 닫는다. 기존 주간 보고/명령 응답의 별도 전송 경로까지 같은 보장을 제공한다고 주장하지 않는다. 정확히 한 번 전송은 보장하지 않는다.

필수 테스트: message_id 없음/잘못된 타입, JSON 배열, 응답 중 연결 종료, 예약 push 실패→전송 0, 예약 원격 저장 후 중단→다음 실행 재전송 0, 전송 성공 후 영수증 push 실패→재전송 0, failed만 재시도, dry-run 파일/커밋/전송 0, 최대 길이 메시지의 명령 보존. 가짜 전송기와 임시 로컬 Git 원격으로 검사하고 실메시지를 추가로 보내 검증하지 않는다.

### F5. 스냅샷을 못 남긴 실패도 stale로 반영

대상: candidates.choose_snapshot/generate, daily_run_state, 후보·알림 테스트.

현재 choose_snapshot은 gz 파일만 검사한다. screen이 타임아웃/프로세스 중단으로 실패 스냅샷을 쓰지 못한 경우, 이전 성공 스냅샷이 시간 한도 내이면 stale=[]가 될 수 있다. cards는 screen 실패에도 렌더하도록 설계됐으므로 이 경로도 처리해야 한다.

- daily_runs의 최신 screen 시도 및 실행 상태와 선택한 snapshot run_id를 대조한다. 더 최신의 failed/started/pending/blocked 실행이 있고 그 실행의 정상 결과가 없으면 이전 카드에 실패/갱신 미완료와 마지막 유효 관측을 표시한다. 지난 실패 뒤 더 최신 성공이 있으면 stale을 해제한다.
- schema 1 이력의 unknown과 실제 실패를 혼동하지 않는다. 해당 상태의 자동 스크린 알림은 0, 조회는 유지한다.

필수 테스트: 이전 성공 gz만 존재+이번 screen timeout, pending 이후 중단, 그 뒤 정상 성공 복구, 시각만 새롭게 재렌더해도 신선해지지 않음.

### F6. 근거 승인과 사용자 화면 마무리

대상: candidates.py, templates/candidates.html, telegram_cmd.py, schema.json, 문서.

- 질문 3/4/12의 상태·승인·추적 표시를 반영한다. 근거 파일을 고친 뒤 예전 index의 버전을 그대로 승인하는 일이 없도록 현재 입력으로 내용 해시를 재계산해 일치 여부를 검증한다. 승인 명령은 알림 전송을 직접 수행하지 않는다.
- 추천은 원문 확인자의 명시적 승인만 허용한다. 다섯 칸에 문장/URL만 있는 것을 실질 검증 완료로 설명하지 않는다. 승인자/시각/근거 해시/관측 참조를 남긴다. 자료 부족·명시적 보강 필요·stale 상태는 신규 승인을 거부한다.
- 운영 자료를 복사한 실제 생성 HTML로 1280px/390px 렌더, 필터, 카드 상세, 명령 복사, 이탈 후보/다른 가설 추적 표시를 확인한다. 테스트 때 거래소를 가짜로 채우지 않는다.
- 결과물은 현재 artifact와 docs 문서라는 점을 사용자에게 정확히 안내한다. 공개 URL이 필요한 GitHub Pages/종목별 페이지는 별도 다음 단계이며 이 검토를 배포 완료로 쓰지 않는다.

## 4. 완료 기준과 다음 제품 작업

구현자는 각 F의 변경 파일·커밋·재현 테스트 결과·기존 192개 회귀 결과를 기록한다. 운영 결과와 모의 실패 시험 결과를 분리한다. 영수증/원장/기존 추적 3종목을 보존하고 실종목을 임의로 등록하지 않는다. 설계 검토 자체는 추가 텔레그램 전송 지시가 아니다.

사용자가 지금 검증을 위해 종목을 억지로 고를 필요는 없다. 모의 /track→수집 연결 및 실패 복구는 구현자가 끝낸다. 실제로 추적하고 싶은 후보를 선택했을 때만 첫 운영 수집을 확인한다. 9/28 주간 단계도 그 날짜 실행 증거로 별도 닫는다.

F 완료 후 우선순위는 **후보의 실적 발표/가이던스 원문을 얕고 넓게 연결해 EPS 상향 원인을 설명하는 것**, 그다음 **종목별 관측 페이지와 접근 가능한 조회 화면**이다. 현재 30개 카드는 숫자 조건을 정리한 발굴 목록이며, 지속적인 이익 증가나 시장 미반영을 입증한 목록은 아니다. 기존 3종목 심층 분석에 다시 작업을 집중시키지 않는다. 이 다음 단계의 상세 구현 지시는 F 검토 후 별도로 확정한다.
