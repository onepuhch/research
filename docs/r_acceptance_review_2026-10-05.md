## 2. 남은 문제: 재시도 5곳이 실행마다 다시 배정됨

- 위치: `scripts/discovery_timing.py:337`, `:353`~`:355`, `:370`~`:374`.
- 현재 날짜별 상태에는 `requests`만 누적된다. `ready[:retries_per_day]`는 호출할 때마다 최대 5곳을 새로 고르므로 같은 날짜의 재실행에서 추가 재시도가 가능하다.
- 재현: 후보 25곳 중 앞 19곳을 가짜 404로 설정한다. 첫날 SPY+19곳으로 20회를 쓴다. 다음 날 첫 호출은 SPY+미시도 6곳+실패 재시도 5곳=12회다. 한 시간 뒤 두 번째 호출은 SPY+다른 실패 5곳=6회를 추가한다.
- 결과: 뒤쪽 정상 6곳은 수집됐으므로 R2의 원래 기아 문제는 해결됐다. 그러나 같은 KST 날짜에 실패 종목 10곳을 재시도해 정책의 일간 5곳 한도를 넘는다.
- 범위: 같은 날 수집 함수를 재실행할 때의 결함이다. 하루 한 번 정상 호출에서 재현되는 문제나 전체 Yahoo 20회 한도 초과로 보고하지 않는다. 실제 Yahoo 요청·운영 사고 증거가 아닌 임시 자료와 가짜 HTTP의 재현이다.

## 3. 구현 담당자에게 넘기는 좁은 보완 지시

목적은 기존 R2의 **하루 재시도 최대 5곳**을 여러 호출에 걸쳐 지키는 것이다. 새 기능·예산·대기 간격은 추가하지 않는다.

- 수정 파일: `scripts/discovery_timing.py`, `tests/test_q3_prices.py`, R 진행/인수인계 기록. 한도는 기존 `config/research_policy.json` 값을 계속 사용한다.
- 날짜 기준은 기존 KST 날짜로 통일한다. `queue.days[day]`에 그날 실제 시도한 실패 종목 재시도 수(예: `retries`)를 영속 저장한다. 계획은 `retries_per_day - 사용량`만 배정한다.
- 요청 직전에 전체 요청 수와 재시도 수를 함께 저장한다. 성공·404·429·5xx·타임아웃 등 결과와 무관하게 실제 재시도 요청은 한 번 소비한다. 결과가 불확실한 중단에서도 이미 예약한 횟수를 되돌리지 않는다. 시간 제한 때문에 요청 전에 중단한 종목에는 횟수를 부과하지 않는다.
- SPY는 전체 요청 한도에만 포함한다. 실패 이력 없는 미시도/정상 재수집 종목도 재시도 한도에 포함하지 않는다. 재시도 몫을 소진해도 미시도 종목은 남은 전체 예산을 쓸 수 있다. 수집할 후보가 없으면 SPY만 요청하지 않는다.
- 날짜가 바뀌면 새 일간 카운터를 사용하고 기존 날짜는 보존한다. 기존 날짜 레코드에 새 필드가 없으면 요청 0건인 날짜는 0으로 시작할 수 있다. 요청이 이미 있는 날짜는 재시도 사용량을 증명할 수 없을 때 남은 재시도 몫을 그날만 보수적으로 소진 처리한다. 같은 날 재실행 때 누적값을 초기화하지 않는다.
- 보고서는 실행별 요청/재시도와 날짜별 누적 사용량을 구분한다. 재시도 몫 때문에 멈춘 것을 전체 20회 소진으로 오인하지 않게 중단 사유를 기록한다.
- 기존 1/3/7일 대기, 실패 집계 보존, 전체 20회 한도, 429/연속 5xx의 당일 중단, 원본 배치 보존은 유지한다.

필수 검증은 다음 범위로 끝낸다.

1. 제공 재현이 1→0으로 바뀌고 둘째 날 첫 호출의 정상 6곳 수집과 재시도 5곳은 유지된다. 같은 날 두 번째 호출의 재시도는 0이다.
2. 같은 KST 날짜의 추가 호출·중단 후 재개에서도 누적 5곳을 넘지 않는다. 실제 HTTP 전에 중단한 계획은 소비하지 않고, 저장 후 요청 중 중단은 소비로 남는다.
3. 재시도 몫 소진 뒤 새 후보가 들어오면 남은 전체 예산에서 수집한다. KST 날짜가 바뀌면 재시도 몫이 새로 생긴다. 기존 필드 없는 날짜의 호환 처리도 확인한다.
4. 기존 Q/R 재현 0, 전체 시험과 CI 통과. 수정 전 증거를 덮어쓰지 않고 수정 후 JSON·커밋·시험 수를 인수인계에 남긴다.

## 4. 운영 확인은 다음 정상 일간에서

검토 시점까지 Q/R이 적용된 정상 일간 실행은 확인되지 않았다. 최신 push CI 성공을 운영 적용으로 취급하지 않는다. 별도 수동 전체 재실행이나 시험 알림 발송 없이 다음 정상 일간의 실행 ID·실제 코드 SHA로 다음을 기록한다.

- 실제 버전: context-v11 / cards-v10 / views-v4 / update-check-v5 / material-update-v3 / discovery-timing-v2. 위 소규모 보완의 SHA도 함께 기록한다.
- 원장 v1→v3 백업 `candidate_alerts.pre_material-update-v3.json`과 기존 발송/예약 이력 보존.
- 후보 시세 첫 배치, 전체/재시도 요청 수, 정상·실패·미시도 집계와 뒤쪽 후보 진행.
- PBF의 두 번째 확인·14일 간격·실제 영수증. 10/9는 가장 빠른 가능일이며 발송 확정일이 아니다.
- CLBK 새 초안 생성과 기존 초안 격리, 업종 묶음 기업의 초안 몫, 503 대기·재개. 해당 사건이 발생하지 않으면 미관측으로 남긴다.

이번 검토의 변경물은 이 문서·합성 재현·증거 JSON·STATUS뿐이다. 운영 코드/원장 수정, push, 모델·SEC·Yahoo 요청이나 메시지 발송은 하지 않았다. CI 확인을 위한 GitHub 읽기 요청만 사용했다.
