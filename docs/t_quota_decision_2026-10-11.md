# 429 관측과 예산 경계 판단

작성: Codex, 2026-10-11 KST. STATUS·S 인수인계 §7·429 기록 코드를 읽고 Google 공식 문서를 확인했다. 실제 Actions 실행·프로젝트 콘솔은 이번에 재조회하지 않았다. 627개 통과는 구현 담당자 보고다. 코드 변경·모델 요청·전송은 하지 않았다.

## 현재 판정

10/11 일간은 운영 실행 성공, 추출 자료 품질 partial이다. 14단계 success를 발굴 내용의 완전성이나 S0-A/B 실제 검증 완료로 표현하지 않는다. ARTW 대기 해소와 notify 적격0/전송0은 관측 결과로 보존한다. 이번 429 경로는 기존 정책이며 503 부분 성공 및 같은 날 장애 복구는 여전히 미관측이다.

18:23Z 실행은 PC commands였다는 정정을 수용한다. 첫 recover 21:51Z의 무계획은 일간 기록 부재에 대한 사전 조건 확인이다. 오늘 복구 기회0은 현재 차단 시각과 예약에 따른 예상이며, 실제 남은 실행의 계획0/보류 사유는 로그를 본 뒤 관측으로 기록한다.

## 확인된 제공자 규칙과 미확인 사항

[Google Gemini API 공식 rate limits 문서](https://ai.google.dev/gemini-api/docs/rate-limits)를 10/11 확인했다. RPM(분당 요청), TPM(분당 입력 토큰), RPD(일일 요청)를 각각 적용하며 어느 한도를 넘어도 오류가 난다. 한도는 API 키가 아니라 프로젝트 단위이고 모델·등급에 따라 다르다. RPD는 태평양 자정에 초기화된다. 실제 적용 한도는 AI Studio에서 확인한다.

따라서 태평양 날짜 경계 자체는 더 이상 미확인이 아니다. 미확인은 이번 429의 종류, 이 프로젝트/모델의 실제 한도, 로컬과 Actions의 프로젝트 동일성 및 전체 사용량이다. 키 동일성만 확인해서는 충분하지 않다. 4회/45초만으로 RPM을 배제할 수 없고 TPM은 요청 건수만으로 판단할 수 없다. 내부20회를 제공자 실제20회로 취급하지 않는다. 대략40회가 한 제공자 날짜에 겹칠 수 있다는 것은 내부 두 날짜의 상한 합계이며 실제 공급자 허용량 또는 이번 원인을 입증하지 않는다.

태평양 자정은 한국 기준 서머타임16시·표준시17시다. 16시 고정값으로 연중 구현하면 안 된다.

## 선택: KST 업무 예산 유지 + 제공자 한도 별도 관리

(a)의 단순 날짜 교체 대신 이중 예산을 선택한다. 일간·기능별 몫20/11/6/3, 복구 횟수, 보고일은 KST 기준으로 유지한다. 프로젝트/모델별 제공자 RPD 한도와 태평양 날짜 계수를 별도로 두고 요청은 두 예산 모두 남을 때만 허용하는 것이 목표다. (b)는 모든429에 일괄 적용하지 않고 한도 유형별로 판단한다. (c) 일간16시 이후 이동은 채택하지 않는다. 수집을 늦추며 타이머·수동 실행이 남아 한도 관리의 대안이 되지 않는다.

지금은 429 증거 기록을 유지하고 차단 동작은 바꾸지 않는다. 실제 한도는 AI Studio의 읽기 전용 확인으로도 확보할 수 있으므로 다음429를 일부러 기다리거나 유발할 필요는 없다. 프로젝트 식별정보·키를 공개 원장이나 문서에 남기지 않는다. 접근 불가하면 확인 대기로 두고 정상 운영에서 나오는 quota 기록을 사용한다.

한도 확인 뒤 구현 범위:

- 대상: scripts/common.py의 예약·잔여량·차단, scripts/extract.py의 quota 분류, config/research_policy.json, 모델 예산/429 시험, README. 신규 제공자 한도는 근거·확인일·모델·비밀 아닌 내부 범위명과 함께 설정한다. quotaValue 하나로 설정을 자동 덮어쓰지 않는다.
- 요청 직전에 KST 몫과 제공자 날짜 몫을 함께 영속 예약한다. 재시도·실패도 내부 계수는 소비한다. 제공자 실제 과금/실패 계수와 같다고 주장하지 않는다. 날짜 변환은 America/Los_Angeles 시간대와 DST를 사용하며 Linux/Windows에서 시간대 자료 가용성을 검증한다. 고정UTC 오프셋 금지.
- 이전 KST 일일 합계만으로 제공자 당일 정확한 사용량을 복원할 수 없다. 시각별 증거로 복원하거나 다음 제공자 날짜부터 시작하며 불명확한 기존 사용량을0으로 초기화하지 않는다. 외부 도구/로컬 사용량이 있으면 내부 계수는 관측한 사용량에 불과함을 표시한다.
- 확인된 RPD 초과는 다음 태평양 자정 전에는 재개하지 않는다. RPM/TPM은 유효한 Retry-After/RetryInfo를 참고해 재개하되 기존 대기·예산·복구 상한을 모두 지킨다. 여러 위반이 함께 있으면 모든 조건이 풀려야 한다. 짧은 retryDelay가 RPD 초과를 무효화하지 않는다. 종류 불명/파싱 실패는 현재 보수적 차단을 유지한다.
- quota 기록은 진단용이다. 응답 구조가 잘못돼도 원래429 차단·상태 저장을 방해하지 않게 하고, 여러 violations·빈값·손상JSON·RetryInfo만 있음도 시험한다. 본문 메시지·프로젝트 번호·키는 기록하지 않는다.
- 완료 기준: KST 자정과 PT 자정 각각의 전후, DST 전환, 저녁→다음 아침의 같은 제공자 날짜 누적, 두 예산 중 하나만 소진, 중단 후 재개, 복합RPD/RPM 위반, 손상 응답을 가짜 시계·가짜 응답으로 검증한다. 실제429 유발시험이나 한도 확대는 하지 않는다.

## 발굴 연구는 기다리지 않는다

PBF → 유조선(DHT 대표) → VSEC 후속 조사는 저장 원문·수작업 비교로 지금 병행한다. VSEC는 EPS 정의 비교를 먼저 한다. 503 발생이나429 진단은 연구 시작 조건이 아니다. thinking 비교만 기존대로 여유 예산 및 실제 한도 확인 뒤 진행한다. 우선순위 조정만으로503/타임아웃/문서 부재까지 해결된다고 보지 않는다.

다음 인수인계는 운영 관측, quota 근거, 후보 조사 진척을 별개로 보고한다. S0의 미관측을 없애려고 장애를 만들거나 수동 전체 실행하지 않는다.
