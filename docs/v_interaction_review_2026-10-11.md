# V 검토·구현 지시 — 알림 답장과 사용자 판단

작성: Codex, 2026-10-11. 대상: V 제안, telegram_cmd.py의 큐/오프셋/추적 처리, candidate_alerts.py의 발송 영수증. 코드 구현·외부 발송은 이번에 하지 않았다.

## 결정

V1(정해진 답장 처리)을 먼저 구현한다. 사용자 선택을 실제 연구 흐름에 연결하는 기능이며 모델 호출0으로 진행한다. V2(명령 확인 간격 단축)는 이번 범위에 넣지 않는다. V3(자유 질문)는 별도 보류한다. V1이 기대차 연구를 대체하지 않으며 U 후속 비교 자료 연구는 계속한다.

사용자 판단은 관심·사용성의 지표다. 시장 미반영, 투자 성과, 근거의 정확성을 입증하는 정답 라벨로 사용하지 않는다. 무응답도 거절로 세지 않는다. 이번 기록을 카드 정렬·자동 추천·알림 억제·모델 학습에 사용하지 않는다.

## V1 동작

| 알림에 보낸 답장 | 처리 | 저장할 의미 |
|---|---|---|
| 추적 또는 인수 없는 /track | 해당 후보에 기존 추적 로직 적용 | track 의도 + 실제 처리 결과 |
| 관심없음 또는 패스 | 사용자 판단 기록 | dismiss |
| 보류 | 사용자 판단 기록 | hold |
| 자세히 또는 인수 없는 /candidate | 기존 상세 조회 | detail 활동(판단 아님) |

앞뒤 공백만 제거한 정확한 낱말을 받는다. 자유 문장을 유추하거나 모델에 보내지 않는다. 기존 인수가 있는 명령은 기존 방식대로 처리하며 답장 문맥이 인수를 덮어쓰지 않는다. 답장 대상 없는 낱말과 알 수 없는 문장은 현재 도움말 흐름을 따른다. '틀림'은 향후 오류 신고 용도로 검토하되 이번에는 추가하지 않는다.

V1은 기존 승인 채팅에서 동작한다. 원장에 채팅 원문·답장 원문·사용자 이름·키를 남기지 않는다. 기존 단일 사용자/허용 채팅 범위를 넓히지 않는다. 여러 사용자의 판단을 합치는 그룹 기능은 이번 범위 밖이다.

## 대상 식별과 오래된 알림

- message_id만 전역 식별자로 사용하지 않는다. 허용된 채팅/봇의 범위 안에서 발송 영수증을 찾아 유일한 이벤트인지 확인한다. 저장 범위 식별자는 비밀이 아닌 고정 내부 별칭을 쓰고 실제 채팅 ID를 공개 원장에 추가하지 않는다.
- 최초 구현은 candidate_alerts의 candidate_id가 있는 sent 이벤트만 지원한다. 발송 당시 candidate_version·event_key와 reply_to_message_id를 고정한다. 명령 회신·정정 메시지168·후보 ID 없는 뉴스/위험 알림·모호한 매칭은 판단을 남기지 않고 원 후보 알림에 답장하라는 안내만 준비한다.
- uncertain/failed/reserved는 사용자 답장만으로 sent로 바꾸지 않는다. 자동 추적·판단 등록도 보류하고 기존 /candidate ID 또는 /track ID 사용 안내를 준다. 본문·티커를 읽어 후보를 추측하지 않는다.
- 과거 후보 버전은 판단의 문맥으로 보존한다. 추적 시 현재 후보와 기존 promote 검증을 사용하되 실제 처리 버전도 기록한다. 오래됨·식별 부족·추적 상한·현재 부적격은 기존 규칙대로 거절하고 성공으로 세지 않는다.
- 알려진 제공처 불일치로 표시된 알림에 대한 판단은 기록할 수 있지만 disputed_source 표시를 연결한다. 이 알림을 통한 추적은 자동 등록하지 않고 최신 상세를 보고 명시적 /track ID로 선택하도록 안내한다. 일반 /track의 기존 권한·검증을 우회하지 않는다.
- 자세히는 최신 상세와 발송 당시 버전이 달라졌는지 표시한다. 관심없음/보류는 현재 추적을 해제하거나 기존 알림 예약을 취소하지 않는다. 회신에도 이 의미를 분명히 한다.

## 기록·재처리 규칙

대상: scripts/telegram_cmd.py, 새 scripts/candidate_feedback.py, data/processed/candidate_feedback.json, scripts/candidates.py의 표시, scripts/discovery_timing.py의 보고, README, 관련 시험. 정책/필드 공통 정의가 필요하면 현행 schema와 policy 관리 규칙을 따른다. 임의 CSV 직접 수정은 하지 않는다.

- 입력 수신은 현재 순서를 유지한다: 허용된 필드로 정규화한 명령 큐를 원자 저장 → Telegram offset 저장 → 처리. 오프셋을 먼저 올리거나 큐를 우회하지 않는다. 큐에는 답장 이벤트 참조와 enum만 추가하고 자유 텍스트를 넣지 않는다.
- 피드백은 추가 전용 events로 저장한다. 최소 필드: 내부scope, update_id, Telegram 메시지시각(있는 경우), received_at, event_key, candidate_id, 발송 candidate_version, reply_to_message_id, action, source. 중복 키는 scope+update_id다. 처리 순서는 update_id로 정하고 동일 업데이트를 다시 읽어도 이벤트는1건이다.
- 의도와 결과는 분리한다. track 의도 이벤트를 저장한 뒤 기존 추적 함수를 호출하고, 결과 이벤트에 operation_key·success/already_tracked/rejected·reason_code·idea_id·처리 버전을 기록한다. 문구 파싱으로 성공을 판단하지 말고 추적 함수가 구조화 결과를 제공하도록 필요한 만큼 분리한다. 실패 이유의 원문 대신 정해진 코드를 저장한다.
- 추적 원장 저장 후 결과 저장 전에 중단돼도 기존 기업+가설 중복 방지를 사용해 등록을 중복 생성하지 않는다. 정상 저장된 판단/추적 결과는 회신 실패 때문에 되돌리지 않는다. 재처리하면 미완료 부분만 실행한다.
- 큐·피드백 파일 손상은 빈 파일로 바꾸지 않고 실패로 남긴다. dry-run에서는 큐·offset·판단·추적 원장 모두 쓰지 않는다.
- 회신은 기존 reply_pending 큐로 보낸다. 이번 구현 시험은 가짜 전송만 사용한다. 네트워크 응답 불명 시 회신의 정확히 한 번 전달은 보장하지 못한다는 기존 한계를 문서화하되 피드백/추적 중복 방지와 구분한다.

## 현재 판단과 평가

detail은 활동 로그에만 포함하고 최신 track/dismiss/hold 판단을 덮어쓰지 않는다. 같은 알림의 판단 변경은 모두 보존하고 마지막 판단을 표시한다. 기업 전체가 아니라 후보+가설을 기준으로 카드에 최신 판단과 판단 당시 버전/날짜를 표시한다. 과거 버전 판단을 현재 버전에 대한 검증으로 표시하지 않는다.

보고 모집단은 지원 가능한 sent 후보 알림이다. 기업 수와 이벤트 수를 별도로 표시한다. 한 이벤트의 여러 답장을 여러 성공 사례로 세지 않는다. 최신판단별 수, 무판단 수, 상세 조회 이벤트 수, 추적 요청과 실제 등록/거절 수를 분리한다. 무판단이면서 detail만 있는 경우도 구분한다. 정정/불일치 표본은 별도 집계한다. report 제목은 사용자 반응/활용이며 정확도·적중률로 이름 붙이지 않는다. 수익률은 기존 평가기간·기준과 결합 가능한 경우에만 나중에 따로 본다.

## 검증과 완료 기준

1. 네 가지 답장과 기존 명령 동작, scope 안 유일한 메시지 연결, 알림 아닌 답장/ID 없는 알림/uncertain 거절.
2. track→detail은 판단track 유지, track→dismiss는 판단 변경/실제 추적 유지, detail만 있으면 무판단+조회로 표시.
3. 추적 성공·이미 추적·상한 거절·오래된 후보·불일치 알림을 구분하고 연구 판정/추천 승격을 만들지 않음.
4. 동일 업데이트 재입력, 큐 저장 후 중단, 추적 저장 후 중단, 결과 저장 후 회신 실패에도 피드백/추적 중복0. 파일 손상·dry-run·원문 미저장 확인.
5. 카드/보고의 분모·버전·무응답·detail 집계 검증. 대표 가짜 입력/예상 회신과 결과 JSON을 인수인계에 남김. 관련 회귀 및 필요한 전체 CI를 통과하되 실제 Telegram 발송 없이 검증.

## V2/V3 보류 조건

V2는 기존 주기에서 V1을 먼저 확인한 뒤 판단한다. 노출된 토큰 문제는 접근권한·비밀 관리 문제로 별도 해결해야 하며 토큰 교체만으로 폴링48회/일을 정당화하지 않는다. 빈 실행의 실제 변경/커밋 여부와 일간 큐 대기·실행 비용을 먼저 읽기 전용으로 확인한다. 30분 폴링은 30분 내 응답 보장이 아니다. 이번에는 타이머·워크플로·토큰을 변경하지 않는다. 새 상시 서버도 만들지 않는다.

V3는 자유 질문에 항상 모델이 필요하다는 전제를 두지 않는다. 저장 카드 조회/정해진 설명은 기존 상세 기능으로 제공하고 자유 문장 해석·근거 답변이 실제 필요할 때 별도 설계한다. 예산 개편 완료만으로 자동 착수하지 않는다.

이번 검토에서는 V 제안과 현행 소스만 읽었고 구현·테스트 실행·모델/API 요청·메시지 발송은 하지 않았다. '일반 답장에는 도움말 회신'이라는 정정은 코드에서 확인했다. 15시 무렵 실행의 상세 무계획 이유는 인증 로그를 읽지 못했으므로 관측 사실로 확정하지 않는다.
