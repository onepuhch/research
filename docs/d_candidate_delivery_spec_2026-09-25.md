## 2. 질문 4개에 대한 결정

### Q1. degraded도 다시 실행할 것인가

**완전 성공과 구분하고, 제한적으로 재시도한다.** 종료 코드 0은 프로세스가 끝났다는 뜻이지 수집 품질이 완전하다는 뜻이 아니다.

- screen은 이번 실행의 snapshot/run_id를 확인해 품질을 읽는다. 이전 run_status의 success를 가져와 이번 실행의 성공으로 쓰지 않는다. failed/not_attempted가 있으면 partial, 정상적인 unavailable만 있으면 기술적 완료로 인정하되 커버리지를 그대로 보여준다. 전체 원천 접근 실패는 failed다.

- D 후보 카드는 partial 결과 중 검증된 행을 보여줄 수 있다. 다만 전 종목 상대 순위는 ‘확보 범위 내 순위’로 표시한다. 신규 자동 발굴 알림은 해당 후보의 필수 자료가 온전하고 최신 수집이 기술적으로 완료됐을 때만 보낸다. 추적 종목 위험 알림은 별도다.

현재 목록은 충분하지 않다. gen_report의 health는 revision_screen/returns 상태를 읽고 research_journal.render는 returns 결과를 읽는다. **screen 또는 returns만 갱신해도 관련 화면은 갱신돼야 한다.**

## 3. D 연결 전 C 보완 — 재개 중 중단과 선행 단계 검사

검토 중 순수 함수로 다음을 재현했다. 모든 단계가 한 번 성공한 날 EPS 재시도가 필요해 eps+views를 계획한다. EPS가 성공하고 views 실행 전에 중단되면, 기존 views 성공 기록이 남아 다음 auto 계획이 빈 목록이 된다. 최신 EPS가 화면에 반영되지 않아도 완료로 판단하는 문제다.

대상: daily_run_state.py, daily_discovery.yml, test_daily_run_state.py.

1. 계획을 저장할 때 이번에 다시 실행할 모든 단계를 pending으로 무효화한다. 이전 성공 정보는 last_success_at/output_revision으로 보존한다. start_run 저장과 무효화는 한 번의 atomic_json으로 처리한다. 단계별 이력 또는 run 내 attempt 목록에 이전/이후를 보존한다.
2. 실행 래퍼가 STEPS의 필수 선행 단계 상태를 직접 검사한다. `steps.extract.outcome != 'failure'`만으로는 collect 실패로 extract가 skipped인 경우 notify/views가 통과할 수 있다. YAML과 Python에 서로 다른 의존 판정을 두지 않는다.
3. blocked 단계는 이유와 dependency_run_id를 기록하고 본문 명령을 호출하지 않는다. 이전 성공이 있어도 이번 계획에서 무효화된 상태라면 사용하지 않는다. 별도 입력 갱신 관계를 사용하는 views는 부분 화면을 만들 수 있다.
4. 성공한 화면/카드는 입력 revision을 저장한다. 새로운 upstream 산출물이 만들어졌으면 같은 날이라도 재생성한다. 코드/정책 변경만으로 수천 건 재수집할 필요는 없으며, 새 화면 생성 버전과 입력 revision의 변경으로 렌더를 무효화한다.
5. 필수 테스트: eps 성공 후 views 전에 종료 → 다음 auto에 views 포함; collect 실패 → extract 명령 미호출; skipped extract를 성공으로 간주하지 않음; screen/returns만 갱신 → 화면 갱신; partial 재시도 쿨다운·1회 한도; commands는 수집하지 않음; KST 날짜 경계.

## 4. D의 사용자 경험과 작업 분할

목표는 ‘왜 후보인지 읽음 → 근거와 한계를 확인 → 사용자가 추적 선택 → 실제 숫자가 누적됨’이다. 신규 종목마다 심층 보고서를 자동 생성하거나 숫자 순위를 투자 추천으로 바꾸지 않는다.

- D2: 사용자가 고른 후보의 원장 등록과 정기 수집 연결.

## 5. 후보 모델과 식별 규칙

새 `scripts/candidates.py`에 스냅샷 선택·검증·후보 변환을 모은다. 카드·Telegram·HTML이 각자 숫자 계산과 순위를 만들지 않도록 동일한 모델을 사용한다.

- candidate_id: `CAN-`+기업 식별자·thesis_key의 SHA256 앞 16자리. 전체 키도 저장하고 충돌을 검증한다. 대소문자/공백/티커 별칭은 기존 resolve_entity 규칙을 따른다. 신규 기업은 검증된 티커로 식별하고 CIK를 추측하지 않는다.
- 스크리너 가설 키 초기값은 `eps-revision-review:v1`. 뜻은 ‘EPS 상향의 사업 원인과 지속성 검토’이며 병목이 이미 입증됐다는 뜻이 아니다. 날짜·순위·대상 FY 변경만으로 새 candidate_id를 만들지 않는다.
- candidate_version: 카드의 판단·수치·근거·대상 기간이 바뀔 때 생성하는 내용 해시. 수집 시각만 바뀌었다고 의미상 새 후보 알림을 만들지 않는다. 각 버전은 source_snapshot 경로와 SHA256, 관측 시각, 정책/생성기 버전을 참조한다.
- 상태를 분리한다: 데이터 품질, 후보 분류(found/needs_evidence/recommended), 사용자 추적 상태(untracked/tracked/closed). 추천과 사용자 선택을 하나의 등급으로 합치지 않는다.
- 숫자는 EPS 현재/30일 전/90일 전, 대상 회계기간, 제공자·회계기준·통화, 실제 주가 시작/종료일, 가격 변화, PER 참고 변화, A/B 순위/선정 이유를 담는다. 없는 값은 null과 reason으로 남긴다.
- 설명은 company_description_ko, earnings_path, persistence_evidence, market_expectation_gap, falsification, next_check를 각각 저장한다. 문장별 출처 ID와 fact/guidance/consensus/interpretation 구분을 둔다.
- source에는 URL, 제목, 제공자, 발표일(모르면 null), 실제 관측일, 인용/정확한 데이터 필드를 보존한다. crumb/토큰 포함 URL과 비밀키는 저장 금지.
- 생성 후보 버전은 `data/processed/candidate_history/{version}.json`에 불변 저장한다. 최신 후보 목록은 재생성 가능한 index로 둔다. JSON 계약도 config/schema.json에서 정의한다. CSV 원장 변경은 add_entry.process만 사용한다. persist_state 허용 목록에 필요한 경로만 추가한다.
- 최신 시도 실패 시 이전 유효 후보를 읽을 수 있지만 ‘마지막 유효 관측’ 날짜와 실패를 표시한다. 새 알림은 보내지 않는다. 기존 시계열·원본 스냅샷은 삭제하지 않는다.

## 6. 카드 내용·추천 기준

카드 순서는 회사/무엇으로 돈을 버는지 → 후보 선정 이유 → 숫자와 기준일 → 확인된 사업 근거 → 미확인/반증 → 다음 확인 → 추적 명령이다. 카드 상단은 ‘발굴 후보’ 또는 ‘추적 추천’으로 정확히 구분한다.

EPS 스크린만 있으면 found다. 회사 설명은 검증된 프로필의 한국어 번역을 사용할 수 있지만 수치·고객·시장점유율을 덧붙이지 않는다. 번역 실패 시 ‘회사 설명 확인 중’과 티커를 표시한다. LLM 연결은 기존 추출 경로/정책을 재사용하고 카드 렌더마다 호출하지 않는다. 원문 해시 기반 캐시를 사용하며 기존 일일 모델 호출 예산을 공유한다.

recommended는 사업 이익 경로·지속 근거·시장 기대 비교의 한계·반증 조건·다음 점검이 출처와 연결되고 사람이 승인한 후보 개정에만 붙인다. 초기 D에서 LLM이 스스로 추천 승인을 만들지 않는다. 승인자·시각·후보 버전을 남긴다. 근거가 바뀌면 이전 승인으로 새 버전을 자동 승인하지 않는다. 사용자는 found도 선택해 추적할 수 있다.

자료 없는 필드를 채우기 위해 웹 전체를 자동 탐색하지 않는다. 이 단계의 목적은 확보한 후보를 읽고 선택할 수 있게 하는 것이다. 선행 가격·공급 신호 확장은 별도 작업이다.

## 7. 조회 명령과 화면

telegram_cmd.py에 `/screen`, `/candidate CAN-...`, `/track CAN-...`를 추가한다. CAN ID 문법은 `CAN-[0-9A-Fa-f]{16}`만 허용한다. 기존 `/track SIG-...`, `/track TICKER`, `/history`, `/list`는 호환 유지한다. 기존 티커 명령을 몰래 새 후보로 바꾸지 않는다.

- `/screen`: 최신 관측 시각, 전체/확보 범위, 후보 수, 표시 순서 상위 5개와 조회 명령. 끝에 명령 처리 주기를 안내하며 실시간 응답이라고 쓰지 않는다.
- `/candidate`: 카드 상세와 해당 CAN ID의 추적 명령. 잘못된 ID, 없는 후보, 오래된 결과를 구분한다.
- command_queue 정규화/허용 목록/재시도 경로까지 함께 수정한다. 임의 사용자 문장을 원장이나 저장소에 기록하지 않는다.
- 응답과 알림은 기존 HTML escaping·메시지 분할을 공유한다. URL은 http/https만 허용한다. dry-run은 큐·원장·발송 상태에 쓰지 않는다.
- 사용자 화면은 `docs/candidates.md`와 `reports/generated/candidates.html`로 제공한다. 동일 모델에서 생성하고 HTML은 티커/상태/분류 필터, 상세 카드, 원문 링크, 날짜·단위·한계, 복사 가능한 추적 명령을 제공한다. 서버 없는 HTML 버튼은 추적 등록을 수행한다고 표시하지 않는다.
- 그래프는 기존 data_history와 연결하되 다른 FY/출처/단위를 이어 붙이지 않는다. 신규 후보의 90일 제공값을 자체 과거 관측 그래프로 꾸미지 않는다. 별도 관측 이력이 없으면 ‘추적 시작 후 관측 누적’이라고 표시한다.
- 데스크톱·모바일에서 카드 가독성과 가로 넘침을 검증하고 실제 렌더를 못 확인했으면 그 한계를 기록한다.

## 8. 사용자 추적과 실제 수집 연결

`promote.py`에 promote_candidate를 추가하되 뉴스 SIG를 가짜로 만들지 않는다. investment_review_log에 origin_candidate_ids를 별도 컬럼으로 추가하고 schema·백업 마이그레이션·검증을 함께 수정한다. 기존 origin_signal_ids는 그대로 보존한다.

1. CAN의 entity+thesis_key로 기존 활성 아이디어를 찾는다. 있으면 같은 idea_id를 반환하고 새 원본 연결만 필요할 때 변경 이력을 남긴다. 같은 명령을 재처리해도 중복 등록·중복 판단 이력이 생기지 않아야 한다.
2. 신규 선택은 현재 단계 관찰, 사업 단계 미확인, 근거 수준 가설로 등록한다. 검토 상태는 기존 enum의 ‘추적’으로 두되 ‘사용자가 추적을 선택함’이지 검증 승격이 아님을 사유에 명시한다. 아이디어 유형은 사이클 리비전형, 가설은 EPS 상향 원인·지속성 검토로 기록한다. 병목 근거를 자동 생성하지 않는다.
3. 등록 당시 candidate_version/source_snapshot/기준 숫자와 미확인 사항을 보존한다. 기존 자동 review_history 기록 경로를 사용한다. 다음 점검일은 review_interval_days를 따른다. 활성 아이디어 상한 10개는 기존 정책을 공유하고 초과 시 일부 쓰기 없이 종료한다.
4. collect_eps.load_targets는 active_ideas를 읽는다. 신규 티커가 entities.json에 없어도 검증된 entity/ticker/통화로 수집 가능하도록 공통 target resolver를 보완한다. 스크리너 provider-unspecified와 기존 non-GAAP 관측을 같은 시계열로 합치지 않는다. 첫 수집의 실제 시각을 baseline으로 사용한다.
5. commands 실행에서 원장 등록 후 바로 수천 종목 스크린이나 외부 숫자 수집을 시작하지 않는다. 답변에 ‘추적 등록 완료, 다음 일간 수집부터 숫자 누적’이라고 쓴다. 다음 auto에서 신규 추적 티커가 빠지지 않도록 추적 대상 revision을 eps/quarterly/prices와 관련 views/cards 입력에 반영한다.
6. source 또는 검증 정보가 부족하거나 후보 관측이 signal_lookback_days보다 오래됐으면 신규 등록을 거절하고 최신 수집 후 다시 조회하도록 안내한다. 기존 추적 조회는 막지 않는다. 영구 입력 오류와 일시 쓰기 오류를 구분한다.
7. 사용자 승인 없이 기존 ALAB/CRDO/MRVL의 가설·판단·추적 상태를 덮어쓰지 않는다. 관찰 가능한 후보 목록에서 사라져도 기존 추적을 자동 종료하지 않는다.

## 9. 신규 알림: 한도·선정·중복

notify.py의 뉴스 후보와 새 스크린 후보가 하나의 KST 일일 candidate 예산(3개)을 공유한다. 명령 응답과 추적 종목 위험 알림은 이 한도에 넣지 않는다. 위험 알림은 신규 후보 처리 실패 때문에 막히지 않도록 별도 단계/선택 경로로 유지한다.

신규 후보 순서: 사람이 승인한 recommended 우선, 다음은 기존 적격 뉴스 후보와 스크린 후보를 번갈아 선택한다. 각 채널 내부 순서는 기존 뉴스 우선순위, 스크린은 A1/B1/A2/B2 순으로 중복 기업 제거한다. 이것은 발송 슬롯 배분이며 통합 투자 점수나 기대수익 순위가 아니다. 한 채널에 후보가 없으면 다른 채널이 남은 슬롯을 쓴다. 날짜별 첫 채널을 교대로 정해 장기 편중을 줄인다.

- 첫 도입에서도 과거 후보를 전부 알리지 않는다. 첫날 최신 자료 중 최대 3개, 선택하지 않은 초기 후보는 조회 목록으로 제공한다. bootstrap 관측집합을 저장하고 다음 날 동일 초기 후보를 ‘새 발견’으로 다시 줄세우지 않는다.
- 알림 논리 키는 entity+thesis_key+event_type이다. 순위·수집일·FY 이동만으로 재알림하지 않는다. 기존 뉴스가 같은 entity+thesis_key로 발송됐다면 스크린 채널에서도 같은 발견을 반복하지 않는다. 키 매핑을 확정할 수 없으면 같은 날짜 같은 기업 후보는 한 번만 알린다.
- 후보 카드 버전은 계속 갱신하되 신규 발굴 알림은 최초 1회만 보낸다. 별도 ‘추적 추천 승인’ 이벤트는 승인된 근거 개정에 대해 1회 가능하며 같은 일일 한도를 사용한다. 가격 몇 % 변화만으로 자동 재알림을 만들지 않는다.
- 알림 문구는 회사 한 줄 설명, EPS 변화/대상 기간, 실제 가격 비교 날짜, 미확인 핵심 1개, `/candidate`와 `/track CAN-...`를 담는다. ‘매수’, 목표가, 상승 확률, 확정 저평가 표현을 생성하지 않는다.
- 발송 원장은 이벤트 키/후보 버전/시도 시각/확인된 message_id/상태를 기록한다. 성공 응답 전에 발송 성공으로 표시하지 않는다. 일부 조각 성공 후에는 미전송 조각만 재시도한다.
- Telegram 수신 후 로컬 저장 전 중단 등은 정확히 한 번 전송을 보장할 수 없다. 응답 유실은 uncertain으로 남기고 자동으로 반복 발송하지 않는다. 일일 한도에는 예약·uncertain 슬롯도 포함해 초과 발송을 막는다. 확정 실패만 재시도한다. 기존 send_message의 bool만으로 부족하면 delivery 결과 타입을 확장하고 호출부를 같이 검증한다.

## 10. 워크플로·저장 연결

cards 단계는 최신 screen 시도와 근거/추적 개정 후 재생성한다. 신규 후보 알림은 cards 이후 실행한다. 기존 notify를 위험/신규 후보 역할로 분리할 경우 한 단계가 다른 쪽 상태를 성공으로 덮지 않도록 component명을 분리한다. views는 카드와 발송 상태까지 포함한 최종 사용자 화면을 만든다.

필수 성공 의존과 입력 갱신 관계를 daily_run_state 한 곳에서 관리한다. 정상 후보 0건은 성공이며 실패와 구분한다. cards가 실패하면 신규 후보 알림만 중단하고 기존 명령 처리·독립 숫자 수집·추적 위험 알림은 계속한다. 부분 원자료 카드에는 품질 경고를 붙이고, 신규 자동 알림은 앞서 정한 품질 조건을 따른다.

새 JSON/CSV/문서 경로는 persist_state 허용 목록에 추가한다. 동시에 로컬과 CI에서 운영 원장을 쓰지 않는다. dry-run은 운영 파일 해시가 전후 같아야 한다. 실발송은 기존 사용자 승인 범위 안에서 최신 후보 최대 1개로 먼저 검증하고 receipt를 남긴다. 문서 검토 자체는 실발송 요청이 아니다.

## 11. 필수 검증과 완료 기준

기존 123개 테스트를 유지하고 다음을 추가한다.

1. 같은 입력으로 같은 CAN/버전, 시간만 다른 재수집의 중복 알림 없음, FY 전환 시 자체 관측 혼합 없음.
2. 미확인 설명/근거/가격은 빈칸 대신 이유 표시, 출처 없는 recommended 차단, 승인 버전 변경 시 재검토.
3. `/screen`·`/candidate`·`/track CAN`의 직접 처리와 실제 큐 처리 경로, 비허용 chat/입력 거절, 메시지 길이·escaping.
4. 반복 추적 명령은 하나의 idea_id, 상한 초과/오래된 후보/부분 쓰기 실패에서 정합성 유지, 기존 SIG/TICKER 동작 유지.
5. 신규 추적 기업이 다음 EPS/분기/가격 수집 대상에 포함됨. 신규 수집 날짜와 baseline 정확, 이전 추적 상태 불변.
6. 뉴스+스크린 합쳐 일일 3개, 같은 기업 중복 억제, bootstrap 폭주 방지, 하루 경계, 확정 실패 재시도, uncertain 자동 재전송 금지.
7. screen 실패 후 이전 카드의 stale 표시와 새 발송 금지, cards 실패와 위험 알림 독립, 신규 추적 revision으로 관련 단계 갱신.
8. dry-run은 네트워크 발송·원장/큐/영수증 쓰기 0회. 데스크톱/모바일에서 읽고 선택할 수 있는 실제 카드 화면 확인.

인수인계에는 변경 파일/커밋, 테스트 개수/결과, 카드 예시 3개(정상·자료부족·추적중), 단계별 운영 상태, 실제 전송 여부/영수증, 미검증 시나리오를 기록한다. 화면만 만들어 놓고 D 완료로 보고하지 않는다. 조회→사용자 선택→중복 없는 원장 등록→후속 수집 대상 반영까지 확인해야 한다. 실제 사용자 선택이 없으면 테스트로 검증한 범위와 실운영 확인을 구분하고 임의로 종목을 추적 등록하지 않는다.
